## 一、动机、范围与排期建议

后续排障改进见[服务发现与写入拒绝诊断计划](service-discovery-diagnostics-v1.md)（S1/S2 已人工验收，S3 未实施）：
补充 Agent 服务列表查询与明确的阻塞原因；运行中编辑单独评审，不据此变更本计划已验收的停服规则。

用户人工验证创建 HelloWorld 页面时，短命令启动 npm 服务后再请求端口不能保持服务可用；模型继续尝试
tmux 和 Docker。当前 W1c 明确在一次调用结束后清理后代，其用途是一次性命令，不是后台开发服务器。
向外部 daemon 提交任务不等于由 Roleplex 托管资源；不能把容器能继续运行解释为已经具备服务管理功能。
此次观察是功能缺口的依据，不是未经调查就认定每次 HTTP 失败都由进程清理造成。

已批准新增独立 **W1d：会话后台服务与进程面板**，放在 W1c 之后、W2a 之前，独立测试、人工验收和提交。
用户已确认本计划及下述最新配额修订；不修改 W1c 已验收的短命令清理语义。

首版目标：Owner 在 single 会话中让 Agent 创建并启动一个本机 HTTP 开发服务，回答结束后服务继续运行；
Owner 可通过 `/ps` 查看状态、端口和日志并停止服务。安装依赖、构建等有限任务仍用 W1c，不由常驻工具包办。

明确不做：

- Docker/Compose、tmux、systemd、远程 daemon 的托管适配；不依赖用户安装 Docker。
- 通用任务调度、cron、任意守护进程平台、自动重启、开机自启、跨应用重启的服务接管。
- Guest 或群聊启动/控制服务，Orchestrator 服务编排，Git/worktree，自动部署或发布。
- 公网或局域网端口自动暴露、反向代理、iframe 预览、域名/TLS、容器或 OS 安全沙箱。
- 自动识别、停止或接管用户已通过 Docker 等方式创建的资源；既有容器必须另行明确授权处理。

## 二、三种生命周期必须分开

| 对象 | 所有者 | 何时结束 |
|---|---|---|
| 消息 / generation / execution | 现有调度器 | 本轮回复、取消或失败后终结 |
| W1c 一次性 Shell | 当前工具调用 | 调用结束、超时或取消时回收其进程树，语义不变 |
| W1d 后台服务 | 登录视图之外的后端服务管理器 | 显式停止、寿命到期、会话/World 生命周期结束或进程退出 |

后台服务保存 World、会话、Workspace Binding 和创建它的 execution/tool call 关联。创建 execution 可以
正常 completed，不能为了保活服务把 generation 永远留在 running，也不能另造一套业务 Trace。
服务 ID 是资源身份；PID 只是某次启动的辅助信息，不能用 PID 代替归属、幂等键或取消凭据。

拟分开保存“审批决定”“启动尝试”“实际服务状态”，避免 approved 被误认为 ready。候选状态：
待审批 → 启动中 → 等待就绪 → 已就绪；停止中 → 已停止。拒绝、过期、启动失败、异常退出、中断和清理待确认
分别保留原因。具体状态值及 wire 字段在编码前写入领域协议，本计划不代表这些接口已经可调用。

## 三、启动、权限与资源使用规则

### 3.1 专用工具与逐次审批

拟提供独立的服务启动、状态查询、有界日志读取、停止工具；模型工具与 `/ps` 使用同一服务管理器和登记数据。
工具名和参数在协议阶段定稿，不复用 `workspace_run_shell` 的隐藏后台参数，也不延长其命令超时伪装常驻。

- 首版仅 Owner 触发、single、active role 与当前绑定工作区双开关启用时可启动。查询和控制同样 Owner-only，
  且必须是会话成员；不允许仅凭知道服务 ID 越权。Guest 只保留现有共享工具卡的安全摘要。
- 每次启动都要独立审批，复用 W1c 的加密、digest 绑定、竞争决定和过期纪律，但批准的操作种类必须明确为
  “后台服务启动”，短命令批准不能拿来启动后台服务。重启等同新启动，必须重新审批。
- 审批页显示完整前台启动脚本、World/会话、冻结的规范 cwd、Shell 类型、声明端口、就绪检查和最长寿命。
  脚本、参数、工作区、端口、探针或限制变化都要重批；不允许批准后替换另一份执行计划。
- 程序必须以前台方式交给监管器，例如 npm 的开发服务；模型不通过 `&`、nohup、tmux、Docker 等脱离托管。
  提示词引导和字符串检查不是安全隔离，不能宣称靠禁止几个命令名就能阻止向 daemon 委托资源。
  W1d 不会封锁 W1c 原有的宿主访问；只管理已登记且确认归属的资源。启动失败或进程已回收也不证明脚本
  没有创建外部容器、文件等副作用，不能据此向用户宣称“主机已恢复原状”。
- 创建请求、执行审批决定和 spawn 前均复核权限、配置、服务配额、端口及工作区使用冲突。
  取消和提交交接不能留下无主进程；重复启动请求只返回同一资源/尝试，不重复 spawn。

### 3.2 已批准的可配置配额与默认值

用户最新修订取代此前“World 4 个、工作区不限、会话固定 3 个”的方案：World 默认 20、工作区默认 5、
会话默认 3，均可由 Owner 在对应范围的设置中调整。其余寿命、日志、生命周期及读写兼容策略已批准。

| 项目 | 首版规则 |
|---|---|
| 审批等待 | 沿用 W1c 的 5 分钟 |
| 启动就绪等待 | 默认 30 秒、主机可配置但最多 120 秒；超时是失败，不是假定就绪 |
| 服务寿命 | 默认 2 小时、主机硬上限 8 小时；在审批页明示，到期主动停止；首版不做续期 |
| World 进程总量 | 默认 20，在当前 World 的设置中由 Owner 调整，跨该 World 的全部会话和工作区统计 |
| 工作区进程数量 | 默认 5，在工作区设置中由 Owner 调整，跨关联会话统计；允许多个服务共享工作区，不再采用不限数量规则 |
| 会话进程数量 | 默认 3，在会话详情中由 Owner 调整，覆盖该会话的全部关联工作区；3 是默认值，不是不可调整的硬上限 |
| 单项停止等待 | 每项先优雅停止，再有界强制回收；每项预算建议 10 秒，失败明确进入清理待确认；不是整批只给 10 秒 |
| 日志内存 | 每服务 stdout/stderr 正文合计 1 MiB 环形保留，持续排空，不能无限积压 |
| 日志读取 | 单次最多 64 KiB，带游标和缺口提示；不是返回整个日志重新解析 |
| 终态日志 | 末尾快照有界加密保存，最多保留 7 天；World 总预算建议 16 MiB，超额优先淘汰最旧终态快照 |
| 网络 | 要求本机 loopback 监听；不自动放开 0.0.0.0、公网地址、防火墙或容器端口映射 |

模型只能在服务端允许范围内提出请求，不能提高主机硬限制、继承完整后端环境或添加凭据。
数量/寿命/输出限制不等于 CPU、内存或网络沙箱；首版不宣称能抵御 Owner 批准的恶意脚本。

配额按 `/ps` 中登记的顶层命令/服务运行实例统计，后台服务和一次性命令共用这三层约束；一个 npm 服务及其
监管器、派生子进程算一个实例，不按 OS 子进程数量重复计费。LLM generation、查询/日志/停止操作不额外
占启动名额，不能让满额状态阻止管理和回收。外部未托管容器不在统计内，不宣称这是全机进程数限制。

- pending/starting/running/stopping 及未确认回收的实例占预留名额，确认从未启动或完成回收后才释放。
  一个实例同时占对应 World、工作区、会话各一个名额，三层必须同时满足，不相加，也不存在子级覆盖父级限制。
- 预留、批准、spawn 和配置变更必须并发协调；失败回滚本次预留，重复请求不重复占位。一次性命令也需接入
  统一登记和配额，不因其运行时间短就绕过统计，但仍沿用短调用结束时清理的语义。
- 三个设置都是范围内持久配置，不是浏览器本地选项；已有 World/工作区/会话通过迁移获得默认值。
  默认值不实时继承：改 World 上限不重写工作区和会话配置，改某会话也不影响其他会话。
- 界面展示已用/预留/上限以及是哪一层阻止启动。只允许 Owner 修改正整数配置，非法值明确拒绝；
  数值存储边界和错误码在 S0 定稿，不把任何默认值再偷偷变成不可提高的硬上限。
- 降低上限不自动停止已运行实例；超额状态可见，新的预留被阻止。尚未 spawn 的请求在批准/启动复核时若
  不能满足新上限，明确拒绝并释放自身预留；不因它已获批就越过最新配额。提高上限不自动执行此前失败的申请。
- 修改上限记录操作者、作用范围、旧值/新值、当时占用与结果，沿用现有审计链路，不混同为停止进程的授权。

### 3.3 与工作区写入和清理的兼容

不能让服务永久占据一个 running execution，也不能在创建 execution 结束后丢掉工作区占用事实。
新增独立的持久服务使用记录，并把现有执行授权、可用性、解绑/删除和 World 切换检查接入同一套冲突规则。

| 服务状态 | 对同一工作区的首版限制 |
|---|---|
| 待审批 / 启动交接 | 预留启动名额；启动前与当前 execution 的独占使用协调，不与其他写执行交错 |
| 启动中 / 运行中 / 单项停止中 | 允许已授权的原生只读操作和状态/日志/停止；Shell 可经 Owner 逐次审批执行，继续计入配额；原生 workspace_write 暂仍拒绝；范围未关闭且配额/端口可用时允许新增服务 |
| 单项已确认回收 | 只释放该项的名额、端口和使用记录；其他服务仍占用该工作区时，不开放原生 workspace_write 或直接删除 |
| 清理待确认 | 保留占用，不允许假定没有进程后继续写入、换 World 或删除工作区 |

2026-09-11 用户批准修订：服务运行不再直接禁止 workspace_run_shell。Shell 始终是任意脚本能力，
不能靠识别 curl 等字符串称其为只读；必须逐次审批，审批界面提示工作区服务占用和可能的文件/服务影响。
原生 workspace_write 暂仍保留占用限制；这不是文件写入隔离，已批准 Shell 以及服务脚本自身仍可能修改文件。
状态工具继续提供真实就绪证据，不承诺 HMR、并发编辑一致性或自动回滚；有破坏性影响时仍建议先停服务再操作。
同一工作区的多个服务独立登记归属、端口与生命周期；清理待确认及批量清理门槛继续阻止 Shell，不放宽权限或配额。
启动交接只短时协调预留和权限，不用一个覆盖整个运行期的互斥锁把“工作区可配置多个实例”退化为只能启动一个。
多个服务自身仍可能写入同一缓存或构建目录，审批时必须提示共享目录冲突风险；允许多个实例不等于具备写隔离。
W3 引入 worktree 后，必须让服务占用继续阻止其目录被清理；该衔接在 W3 复核，不提前实现 worktree。

## 四、就绪不是进程创建成功

`npm run dev` 被成功 spawn 只表示启动了命令，不表示页面能访问，更不能把日志出现 URL 当成 ready。

1. 原子预留声明端口及启动名额；启动前检查端口被占用时失败，不自动杀死占用者、不静默换端口。
2. 持续确认受托管进程仍存活，并核对监听端口属于其实际进程树。已有别的服务返回 200 不能冒充本次成功。
3. 对审批中固定的 loopback 地址、端口和相对路径进行 HTTP GET；默认期望 2xx，可在受限范围内配置状态码。
4. 达到证据门槛后由后端发出 ready 状态与探测时间/状态码；启动工具才向模型报告成功。失败停止本次进程并释放
   已确认可释放的预留，保留安全失败原因及有界诊断。
5. ready 后仍监测进程退出和健康变化。进程存活但 HTTP 不可用应显示“不健康”，不伪装成已退出或自动重启。

探针不是任意 URL 抓取工具：固定数值 loopback 地址，不做 DNS、不使用环境代理、Cookie 或用户提供的认证头，
不跟随重定向，不把响应正文写日志或返回模型；连接、读取和响应大小均有上限。平台不能可靠证明监听归属时
明确降级/拒绝就绪，不能用一次 200 填补证据缺失。

脚本偏离声明端口或监听到非 loopback 时不得报告 ready，并停止已登记进程。这是运行后检测，不是防火墙，
不承诺恶意程序从未短暂绑定其他地址。需要强网络隔离时必须另立 OS 沙箱方案。
UI 标明地址属于后端主机；远程 Owner 的浏览器 localhost 不等于后端 localhost，首版不为解决预览而自动暴露网络。

## 五、`/ps`、日志与停止交互

- 输入框整条内容恰好为 `/ps` 时走本地控制入口，不调用 LLM、不创建聊天 generation；引用、代码块及普通
  句子里的 `/ps` 按普通文本处理。也提供可访问的“会话进程”按钮，不要求用户记命令。
- 面板分组展示当前会话登记的后台服务和当前一次性命令，待审批项明确“尚无进程”。只读查询不能申请 Shell、
  调用系统 `ps` 全量扫描、猜测 Docker 容器归属或暴露其他会话/World 的进程。
- 每项显示稳定资源身份、来源角色/execution、状态、工作区名称、声明/实际端口、开始时间和到期时间。
  PID 仅供 Owner 辅助排障，操作按资源 ID 和真实进程句柄/出生身份完成，防止 PID 复用误杀。
- 提供详情、刷新状态、有界日志展开和停止操作；脚本、规范路径、原始日志始终走 Owner-only 接口。
  不把这些正文复制进共享消息、普通 WS、历史缓存、localStorage、机器日志或测试失败产物。
- 后台服务日志沿 stdout/stderr 各自顺序返回，跨管道只能声称“后端观察顺序”；环形淘汰/重连须报告缺口。
  慢客户端或持续输出不能阻塞排空，也不逐输出块写数据库事务或机器日志。
- 模型可调用同源的状态/有界日志工具排障；这些读取也必须验证 Owner、会话归属和工具权限，内容会进入
  当前模型上下文，这一点在启用说明中明确。Guest 没有这些读取能力。
- “停止服务”与“停止生成”是两个动作：前者针对指定资源，后者不隐含杀死已完成移交的服务。
  面板可单独取消待审批启动，但不能把取消误记成“曾启动后成功停止”。

## 六、取消、退出与重启策略

| 事件 | 首版默认行为 |
|---|---|
| 创建工具还在审批/启动/就绪等待时停止生成 | 取消申请或停止本次启动，完成回收；不得留下半移交服务 |
| 服务已 ready、启动工具已成功移交后停止后续生成 | 服务继续运行；通过 `/ps` 的停止入口单独停止 |
| 回答完成、切换会话、刷新页面、WS 断开 | 不停止服务；新页面从后端登记恢复面板，不靠浏览器保活 |
| 退出登录 | 不把身份退出当作全局服务停止；随后私有读取/控制立即失效，服务仍受寿命/World 生命周期约束 |
| 归档/置顶会话 | 不停止服务 |
| 删除会话（含进回收站） | 删除确认同时明确告知会停止该会话进程；关闭该会话启动入口，取消待审批/启动中任务，逐项回收由它启动的一次性命令及后台服务；全部确认后再完成删除，不误停共享工作区内其他会话的服务 |
| 删除工作区登记 | 确认列出受影响会话和进程；关闭该工作区启动入口，跨会话逐项回收关联的所有托管命令/服务，确认后再删除登记；不删除物理目录，不删除会话，也不影响这些会话在其他工作区的资源 |
| 解绑/更换会话工作区 | 确认并停妥该会话在旧工作区的相关进程，再变更绑定；不能因换绑让旧进程失去归属，也不能停止其他会话的服务 |
| 停用服务能力 | 确认并停妥对应授权范围内的服务后再完成变更；回收失败不伪装成停用已完成 |
| World 切换、备份、删除 | 先停止相关服务并确认释放，失败则阻止操作，避免双 World 运行或不一致备份 |
| 应用正常退出 | 全局关闭启动入口，按确定顺序逐项回收本应用实例登记的全部相关进程及后代；逐项写结果后汇总、刷出日志，再关闭日志/数据库和监管资源；不能只关闭 UI 或取消 asyncio Task |
| 后端崩溃/重启 | 不自动重放脚本、复用旧批准或盲目按 PID 接管；核实遗留进程，确认退出才释放占用 |

必须定义“启动成功移交”与取消的原子竞争点：移交前由请求负责取消收尾，移交后由服务管理器负责生命周期。
客户端没收到响应时可以凭同一幂等身份查询真实结果，不能因此再次 spawn。
每个服务只有一个明确的 reducer/宿主任务写状态，用户停止、Agent 停止、寿命到期和进程退出通过事件/CAS
合流；已退出的结果不能被迟到回调改回 running。

Linux 监管器需监测与后端的可靠控制通道/父宿主存活，宿主消失时清理普通后代；Windows 使用在交付脚本前
建立的 Job/句柄归属。不能只记录 PID 后希望下次启动补杀，也不能把关掉日志管道当作已回收证明。
无法验证遗留资源身份或回收结果时进入清理待确认，展示 Owner 诊断入口；不得杀同 PID 的陌生进程或静默释放
端口/工作区占用。监管不是 OS 沙箱，不能保证抵抗提权、杀监管器等恶意行为。

### 6.1 统一批量回收流程（已明确要求）

删除会话、删除工作区、World 操作和应用退出都复用一个回收协调器，不能各写一套按 PID 杀进程的逻辑。

1. **先封闭范围**：在短事务中建立可恢复的回收操作身份和范围门槛，阻止范围内新的申请、批准后启动与服务
   移交；取消该范围内待启动意图。与已在途 spawn 原子协调，句柄尚未交接的实例也必须纳入收尾，不能漏到清单之外。
2. **冻结目标清单**：按 World/会话/工作区/应用实例的登记关系选择目标，记录纳入原因和清单版本。
   不能按命令名、cwd 字符串、端口或裸 PID 猜归属。去重同一资源，保留子进程属于哪个受托管根的证据。
3. **确定顺序逐项处理**：首版不存在跨服务依赖编排，按启动尝试的稳定顺序逆序回收，同序号以资源 ID 固定排序；
   待审批项取消而非伪记为已启动进程。每项完成验证或到达失败终态后再处理下一项，不同时批量发 kill 后假设全部成功。
   单个服务内部的父子回收仍交给其监管器，不按数据库记录顺序粗暴杀父子 PID。
4. **每项验证**：动作前复核资源代次、监管句柄、PID 出生身份与授权范围；先请求优雅停止，必要时强制回收，
   再验证实际退出、已知后代和自身监听释放。发现 PID 复用/归属不符则拒绝杀死该进程并记录原因。
5. **失败不短路**：单项超时、拒绝或未知结果要留在清理待确认，并继续尝试清单中的其他项。已退出实例作幂等
   确认，不重复停止；重复或重叠的删除/退出请求复用该实例的唯一收尾任务，并关联各自触发操作，不记录多次实际关闭。
6. **对账再提交资源变更**：重新对照门槛下的登记和实际监管资源，汇总计划数、取消未启动数、已退出数、
   成功回收数、失败/未确认数及仍在途的启动交接。不能只对已经尝试的子集报“全部完成”。
   有未确认项时不完成会话/工作区删除、不释放相关占用；已停进程不会因删除失败自动重新启动。
7. **关闭基础设施**：应用正常退出时要先完成进程回收与结果持久化，再关闭数据库和日志。每项有界等待，
   整批预算按冻结清单规模计算，包装器/启动器的优雅退出预算必须覆盖它；不能沿用固定短等待截断后一半清单。
   外部系统强杀或预算仍被耗尽时，不写虚假的成功终态，保留未完成清单供下次启动核查。

“应用关闭”指后端及其产品包装器的正常退出路径，包括对应关闭按钮或可处理的终止信号；浏览器标签关闭、
刷新或登录退出仍不等于关闭后端。无法捕获的强杀、断电不保证最后一条日志写出，因此必须在停止前持久化
目标意图并由监管器处理宿主消失；下次启动把恢复观察与旧未完成操作关联，不能补造原时刻的成功日志。
现有 W1c 临时命令及已由应用登记的辅助运行资源也要纳入正确的退出层级；全机陌生进程、外部 Docker daemon
创建的未托管容器不在清单内，不能为了凑齐数量越权回收。

### 6.2 回收日志必须能定位误关和漏关

这是机器审计要求，与服务 stdout/stderr 的 Owner 私有执行日志分开。具体事件名、字段、终态和错误码在 S0
先登记到日志 v2 及对应协议，复用现有 request/chain/execution 关联；回收操作身份是资源操作身份，不另造 Trace。

- **范围与意图**：记录触发者/系统触发源、明确原因（会话删除、工作区删除、应用退出等）、应用实例及 World，
  目标会话/工作区身份、清单版本、预期数量和逐个目标。清单可以分条有界记录，不能只记一个总数或截断目标 ID 列表。
- **逐项过程**：每项记录批次内序号、服务/命令/启动尝试身份、原始会话/工作区/execution 归属、纳入范围的依据、
  PID 及出生身份/监管身份、动作前状态和验证结论；记录开始、优雅停止请求、必要的强制升级、重试以及最终观察。
  PID 和身份只作为有界诊断，不记录整条进程命令行、脚本、环境或路径原文。
- **结果与耗时**：区分从未启动、已自然退出、实际停止、拒绝误杀、超时、回收失败和结果未知；保留停止原因、
  稳定错误码、耗时、退出码/信号（仅已观察时）以及尚未回收的登记后代/监听证据，不把“发出停止信号”记成成功。
- **批次对账**：输出清单与结果的可核对汇总、未处理/失败目标引用、最终剩余数，以及删除/退出是否真正完成。
  单项只记录一次事实，汇总引用它；跨日志轮转、异步任务和包装器的关联不能丢失。
- **诊断目标**：给出任一被关闭资源，能追溯“谁因什么操作、为何选中它、采用何种动作、何时确认退出”；
  给出一次删除/退出，能列出本应回收的全部目标以及漏项停在哪一步。未产生终态的操作必须可检索，不能默认为成功。
- **日志故障**：删除等可拒绝的操作若无法可靠记录回收意图，应在发出破坏性动作前失败；关机/宿主消失不能因
  日志故障放任进程遗留，应继续尽力回收并明确记录可保存的缺口，恢复时不猜测无法观察的结果。

该日志方案用于定位误关、少关的根源，不代表对未托管资源或不可捕获断电具有全量观察能力。

## 七、实现切片与契约职责

### S0：实施前复核与协议定稿

确认本计划的范围、默认值和生命周期；反查现有审批状态机、执行 lease、World 包装器及日志保留规则。
评估服务身份、启动尝试、运行期使用记录和终态日志快照的表结构；必须有 Alembic 迁移、SQLite 重放和
PostgreSQL 重放或至少离线编译，并同步数据模型文档。脚本仍用途隔离加密，原始日志是受保护业务数据。
同时定稿并迁移 World/工作区/会话三层配额配置、旧数据默认值及并发版本，禁止只在前端限制数量。

协议入口只加领域链接；在独立领域文档定稿 REST/模型工具/WS、权限、版本、幂等、并发、错误码、日志游标、
缺口和恢复语义。复用既有 Trace，先登记必要生命周期事件、终态与允许字段，不引入另一套进程日志事实源。

### S1：受托管运行时与确定性后端测试

先写失败测试：审批前无进程、原子启动/取消、独立于 generation、端口/工作区竞争、归属隐藏、就绪证明、
双流限额、正常/强制停止、宿主崩溃与 PID 复用。再实现服务管理器、进程登记和现有授权/World 钩子的必要接入。
统一实现逐项回收协调器、范围门槛、冻结清单和日志对账，不能最后再给删除/退出补一个粗略 kill 循环。
复用 W1c 进程安全基础，不修改其默认短命令收尾，也不把“设置 timeout=None”当作服务管理。

### S2：`/ps` 和浏览器闭环

接入审批卡、进程面板、状态变化、日志分页和停止；从真实后端确认恢复状态，覆盖迟到响应、切换身份、
重连、长日志、页面卸载与滚动保持。一次性命令登记也进入同一会话进程面板，不引入全机进程管理器。
在 World 设置、工作区设置、会话详情提供对应上限编辑及占用提示，三处都显示服务端实际配置和权限错误。

### S3：真实场景与人工验收

在本轮独立 World/外部工作区验证 HelloWorld 页面、npm 启动和指定测试端口（如 52525），通过独立请求拿到
预期页面；回答结束后仍可访问，`/ps` 能查日志并停止，停止后确认托管监听已消失。依赖准备与后台启动分开记录，
不让 npm 下载失败掩盖运行时结果；测试端口被他人占用应报告环境冲突，不停止陌生服务。

自动验证完成后交用户人工验收。S0–S3 是同一 W1d 内部步骤；W1d 独立提交之后才继续 W2a，不顺带实现 P2 或 C。

## 八、验收清单

- happy path：真实前后端 + fake Provider 发起前台开发服务 → Owner 审批 → 后端证实 HTTP ready → 回答结束
  和刷新/切换会话后仍能访问 → `/ps` 读取有界双流 → 停止后所有登记后代与端口释放。
- 关键失败：未批准、拒绝、过期、无权限、跨会话/World、端口冲突、错误状态码、探针重定向、其他进程返回 200、
  程序提前退出、就绪超时、持续大量日志、停止失败和工作区写冲突；不能伪造 ready 或 stopped。
- 并发使用每轮全新迁移库：重复启动、批准与取消、spawn 交接、端口/配额预留、停止与退出、World 操作竞争；
  结果不得重复执行、静默覆盖新版或误杀 PID 复用对象。
- 数量矩阵：默认同会话第 4 个、同工作区第 6 个、同 World 第 21 个预留明确拒绝，分别隔离其他层的限制验证。
  Owner 调高任一层后可突破该层默认值，但仍受其他两层约束；多个会话可共享一个工作区的配额。
  调低上限不杀已有实例，未启动请求必须重新检查；重试/取消/失败/清理待确认不会泄漏或提前释放名额。
  验证一次性命令与服务混合占用、子进程不重复计数，以及满额时仍可查询日志和停止。停止其中一个不得释放其他实例的使用记录。
- 配置矩阵：三处设置持久化、旧数据迁移默认值、非法值拒绝、Guest/跨 World 越权、并发配置修改与 spawn 竞争，
  以及配置变更审计的范围和前后值完整性。
- 删除矩阵：删除会话回收它在所有关联工作区的进程，保留同工作区其他会话进程；删除工作区回收关联的所有
  会话进程，保留这些会话在其他工作区的资源；应用退出回收本应用登记的全部相关进程，不误杀旁路测试进程。
  这些场景同时覆盖临时命令、后台服务、待审批、启动交接和停止中状态。
- 逐项失败与日志矩阵：中间项超时/失败仍继续后续项，重复和重叠回收不重复关闭；最终清单对账能定位未处理项。
  注入 PID 复用、日志写失败、轮转及进程中途强杀，验证误杀拒绝、未完成操作恢复和可追溯性；删除不能越过清理失败。
- 真实断线/重连和后端硬退出测试核对事件序列、最终登记与实际进程；快照和日志游标缺口有可见降级。
- Playwright 实际操作 `/ps`、审批、查看日志、停止，保留一条成功与权限/失败路径；使用 fake 截图检查页面。
  测试数据库、外部工作区和日志均按类别/轮次/用例分层，保留规则复用测试指南，结束清理全部服务进程。
- 独立 real Provider managed-world smoke 必须运行：模型实际启动经批准的测试服务、读取状态/有界日志并回答；
  运行前说明联网计费，Key 只进入后端加密边界，关闭真实截图/trace/video，失败只存安全阶段标签。
- Linux 验证脱离进程组后代及后端被杀场景；Windows 验证原生服务启动、UTF-8、Job 和后端消失后的清理。
  未具备实机证据的平台不得默认开放该平台的后台服务能力；W1c 的既有 Windows 覆盖缺口不能自动算作 W1d 通过。
- 不接管 Docker，不修改用户已有容器或全机进程；文档和模型提示明确未托管资源不会出现在 `/ps`。

## 九、已确认决策

用户已批准其余四项，并最终修订数量策略。删除会话、删除工作区、关闭应用要回收正确范围内的进程，
逐项处理且日志可追查误关/漏关；这项要求继续生效。

1. 将 W1d 插在 W1c 与 W2a 之间，首版限 Owner single、本机 HTTP 开发服务，不包含 Docker 和部署发布。
2. World 默认 20、工作区默认 5、会话默认 3，分别在对应设置/详情中可调；默认 2 小时寿命（主机最多 8 小时）
   和有界日志方案保持已批准规则。
3. 刷新/切会话/回答结束不停止；启动移交后停止生成不停止服务；应用退出和 World 操作需回收，重启不自动恢复。
4. 同一工作区允许多个后台服务；按 2026-09-11 修订允许逐次批准的 Shell 与服务共存，原生写工具占用限制保留，
   不将这种限制解释为文件写入隔离。HMR 并发编辑以后单独扩展。

计划已获批准，按 S0–S3 实施；未经用户验收与提交授权不自动提交。
