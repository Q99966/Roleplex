## 一、目标与阶段门槛

本计划解决切换会话时主动断开连接、长会话首次全量加载，以及阅读历史时滚动位置不稳定的问题。
用户于 2026-09-10 确认以下顺序：

1. **A：连接与会话组件解耦。** 完成自动验证后交用户人工验收。
2. **A 人工验收明确通过后，才进入 B：最近内容分页、会话缓存与滚动位置。** B 同样独立验证、人工验收和提交。
3. **C：单条超长消息分块与进一步渲染优化，延期。** 等内容协议成熟后重新设计与确认，不是本次 A/B 的隐含交付。

自动测试通过、等待一段时间或默认选项不能代替 A 的人工验收，不得把 B 顺带实现进 A。
用户已完成人工验收并提交 A，随后授权开始 B；本轮不实施 C。A/B 不开放 W1c Shell、Repository、MCP 产品接入或 Orchestrator。

## 二、改造前的现状与问题

- 前端按会话 ID 重建 ActiveWorkspace，组件卸载调用全局 closeConversation，直接关闭 WebSocket。
  新组件先等待整个历史请求，之后才新建连接；等待期间沿用 closed 状态，于是正常切换显示成“连接已断开”。
- 后端同一 WebSocket 已能处理后续 subscribe，并替换旧订阅，不要求每次切换重新握手。
  但 auth_ok 仅代表认证；现有 subscribed 在 backlog 回放之前发送，不能直接当作同步完成。
- 历史 REST 与恢复快照均读取全部消息，没有分页；长会话增加数据库读取、传输、解析和渲染成本。
- 前端 messages 一变化就滚到底部，这与向上加载和阅读历史冲突。
- 已实现的工具详情单独鉴权、加密和按需读取，不属于共享历史正文；本次继续保持这个边界。

## 三、A：连接与组件解耦

### 3.1 资源归属

- 连接由登录会话级的连接管理服务持有，与当前后端实例、World 和登录身份绑定；不由某个会话页面拥有。
- 会话组件只选择当前会话、注册/解除页面监听。卸载组件、切换会话和 React StrictMode 的重复挂载不能关闭
  登录会话仍在使用的连接，也不能清空新会话的状态。
- 正常切换复用连接，服务端同一连接仍只保留一个活动会话订阅；不引入同时订阅所有会话的产品能力。
- 回到空工作台时取消订阅但保留连接，需要补齐取消订阅及确认语义。
- 退出登录、切换 World、替换认证上下文或结束应用会话时释放连接、监听和请求。真实断线后重新认证，
  只恢复当前有效订阅；不能恢复已经取消的会话选择。

### 3.2 状态由实际事件驱动

将连接状态与会话内容状态分开，至少能表达：

| 范围 | 状态依据 | 页面语义 |
|---|---|---|
| 连接认证 | socket 建连及后端认证响应 | 正在连接/认证，不冒充会话就绪 |
| 历史加载 | 当前历史请求发起、成功或失败 | 正在加载会话/加载失败 |
| 会话同步 | 订阅受理与后端回放/快照同步完成确认 | 正在同步/可以接收实时更新 |
| 真正掉线 | 非主动取消的连接关闭或错误 | 正在重连/连接异常 |
| 无选中会话 | 取消订阅确认 | 连接可保持待命，不显示故障 |

后端在恢复数据发送完成后发出明确的就绪确认，并给出对应会话、订阅操作身份和同步水位。
前端只有在对应数据已应用后才将该订阅标记为就绪。控制确认不充当业务事件，不另造业务 Trace，也不消耗
消息事件序号。完整字段与兼容方式在 A 编码前写入 WebSocket 领域协议。

不能靠“超过 200 毫秒/1 秒”判断加载、成功或故障。网络超时与重连退避只承担故障兜底，不能伪造就绪状态。
历史加载慢时保持真实的加载/同步反馈，不显示错误的断线提示；A 不承诺解决长历史全量加载的性能问题。

### 3.3 快速切换与一致性

- 连接代次、订阅操作和历史请求都有明确归属；A → B → A 时，迟到的旧成功、错误、断线或取消回调不能
  修改当前 A。仅比较会话 ID 不足以区分两次打开同一个会话。
- 取消订阅只影响对应操作，不允许旧组件 cleanup 关闭新连接或取消新订阅。
- 历史请求的取消、失败、超时和重新打开必须可收尾；请求复用不能让新打开永久挂在一个旧 pending 请求上。
- 保留首帧认证、资源成员校验、Token 撤销、epoch、event_seq、revision 和 delta_seq 的既有安全与恢复语义。
- 保持工具在正文中的位置、Owner 私有详情隔离，以及生成中切走/切回后的停止和状态恢复行为。

### 3.4 范围与验收

主要改造前端连接管理、聊天状态和组件生命周期，以及后端订阅控制确认；继续使用现有消息正文、工具 part
和历史响应内容。**不在 A 实施分页、历史缓存、超长消息拆分或虚拟列表。** 原则上无需表结构变更。

A 必须验证：

- 同一登录上下文内 A/B 反复切换不新建物理连接；React 重挂载、回到空工作台不会造成错误关闭。
- 后端延迟历史返回或同步确认时，界面准确显示所处阶段；主动切换不显示“连接已断开”。
- 快速 A → B → A、迟到响应、旧订阅错误和重复/乱序帧不会串会话或回退较新状态。
- 真实掉线、认证失效、服务重启、World 切换能正确重连或退出，不泄漏旧 World 消息与 Owner 详情。
- pytest/WS 覆盖生命周期与恢复；Playwright 使用真实前后端、fake Provider 覆盖切换、慢响应、重连与权限路径。
- 复用 fake managed-world 和独立 real-world 测试入口完成世界与真实生成链路验证；真实命令运行前说明联网计费，
  凭据只在后端加密边界内使用，禁止在浏览器产物保存敏感内容。

自动验证通过后交用户人工反复切换验收。**在用户明确确认 A 通过前，B 不得开始。**

## 四、B：最近内容分页、缓存与滚动位置

### 4.1 “分页”的含义与体积边界

B 以**完整消息**为分页单位，但不只按条数决定页大小：同时考虑消息数上限和响应 UTF-8 序列化体积预算。
用户于 2026-09-10 将预算定为最多 50 条、目标 64 KiB；具体响应计量规则见消息领域协议。
预算按未压缩的实际返回表示计算，不能用字符数、压缩后的网络大小或省略未计数的元数据替代。

按时间顺序从最近消息向前收集，先达到任一限制就结束本页；返回给页面时保持消息正序。使用稳定排序键
和不透明游标，不使用新增消息会导致位置漂移的 offset；不得跳过中间较大的消息去塞更小的旧消息。
数据库查询必须采用有界候选批次，不能先读完整会话再在内存截成一页。

**保留一个明确例外：单条消息自身超过体积预算时，仍作为独立一页完整返回，并明确标记超预算。**
该规则确保游标能前进、正文不被静默截断，也不改变一条回复的气泡、消息身份、工具顺序或 Markdown。
因此 B 的体积值是普通页的预算，不是无条件硬上限；单条超长消息的等待和渲染成本仍可能较高，这是延期 C
的已知限制，不能宣称已解决。若后续要求单条也严格限量，必须转入 C 重新确认内容协议。

### 4.2 历史窗口与恢复衔接

- 首次打开只读取最近一页。向上翻阅再获取更早一页，返回后按消息 ID 和 revision 去重合并。
- REST 分页响应与 WebSocket 恢复快照必须协同调整：快照兜底也返回受预算约束的最近窗口和继续读取的能力，
  不能在重连时又悄悄拉取整个会话。
- 活动 generation、停止能力与当前事件水位不能因分页遗漏；未加载区域的增量不构造残缺消息。
  需要显示或定位该消息时再按完整消息补取，保持已加载窗口的连续性。
- 向上翻页不能推进或回退实时订阅游标。历史页读到旧 revision 时不能覆盖已经到达的更新。
- epoch 变化、回放缺口或快照降级后明确作废/重新验证缓存页，不能把旧页拼成“已同步”的历史。
- B 沿用现有单条正文与工具事件内容；超长 message_part_update/message_done 的重复完整传输优化留给 C，
  不把内容协议重构夹带进历史分页。

### 4.3 缓存与阅读位置

- 缓存按后端实例/World、登录会话和会话 ID 隔离，只存共享消息、历史游标、同步水位和阅读锚点。
  不把 Token 原文或 Owner 工具详情加入缓存索引、诊断或持久化浏览器存储。
- 切回已访问会话先显示已有窗口，再后台校验同步；有缓存不等于已经实时就绪。
- 对缓存总字节数和会话数量设上限，按 LRU 等确定策略淘汰；不是仅给缓存条数设上限。退出登录和 World
  切换清空对应上下文，待返回请求也必须失效。单页超预算例外不能使缓存无限增长，可选择不缓存该页。
- 每个会话保存可恢复的消息/工具位置锚点与相对偏移。前插旧消息、Markdown 完成布局或展开工具详情时保持
  阅读位置；不再在 messages 任意变化时滚到底部。
- 用户处于底部时跟随新消息；阅读旧内容时显示新消息提示，由用户决定回到底部。翻页失败保留当前内容与
  位置，允许局部重试；不整屏清空或切换成连接故障。

### 4.4 范围与验收

B 变更历史查询/恢复窗口与客户端数据管理，不拆分数据库 Message，不改 ContextBuilder 的模型历史选择。
界面只取一页不能让模型也只看到这一页。是否需要新增大小统计等存储字段，先评估再按迁移纪律实施，
不提前承诺没有 schema 变化。

B 必须验证：

- 大量短消息、少量长消息、代码/Unicode、多工具回复及单条超过预算的消息；首屏读取不随整段历史线性增长，
  单条例外按前述限制报告，不虚报恒定耗时或硬体积上限。
- 连续向上翻页无重复、无遗漏；并发新消息、生成更新与翻页交错时不覆盖新版、不移动阅读锚点。

- Owner/Guest、World 与登录上下文隔离，工具顺序和 Owner 详情权限保持；后台 ContextBuilder 不受显示页影响。
- pytest/WS 与 Playwright fake 覆盖上述行为；复用 managed-world 和独立 real-world 验证真实消息/工具链。
  测试目录按类别、轮次和用例分层，截图/报告遵守脱敏边界，结束后清理服务。

B 自动验证后单独交用户人工验收，不因 B 完成而自动开始 C。
