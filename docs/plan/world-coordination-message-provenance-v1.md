# 世界管理者身份、消息来源与任务广播修复计划 v1

日期：2026-09-23。状态：**R1–R4 已接入，修复与回归记录见[验收](../testing/workflow-communication.md)**。本次修改公共代码并使用隔离数据验证；真实 World 在正常启动升级时适配原记录，不重放旧任务。

本计划承接[世界类型与桌宠协调基础](world-orchestrator-foundation-v1.md)落地后的实际使用反馈，采用范围为固定世界管理者身份、准确署名与收件人、任务广播、执行输入及上下文来源修复。用户已确认现有“对话与查看 / 执行世界任务 / 补充当前任务”交互可以保留，本轮不改成自然语言自动提权或默认执行。

本文保留本次范围与取舍；最终契约见[协作通信](../protocol/public/rest/workflow-communication.md)和[固定世界管理者](../protocol/public/rest/world-orchestrator.md)。下文的目标已按实际结果落地，代码结构与字段以领域协议为准，不作为新的跨任务审批限制。

## 1. 修复前核实的问题

只读核对实际记录后确认：一次群工作流包含三个角色工作节点，每个节点只有一个执行尝试。群里连续出现的三份任务目标来自三个节点各自的执行输入，并非创建了三次工作流。

| 位置 | 当前行为 | 后果 |
|---|---|---|
| [世界任命服务](../../backend/app/world_orchestrator/service.py) | 首次绑定普通角色后才建立岗位会话，界面使用该角色作为世界管理者身份 | 岗位身份、普通角色及配置来源容易混淆，尚无创建世界时的专用管理者 |
| [群规划入口](../../backend/app/workflows/planning.py)、[工作流执行器](../../backend/app/workflows/engine.py) | 委派、启动和各节点输入都以 user/Owner 写成消息；每个工作节点拼接完整总目标 | 自动安排看起来像 Owner 连续发言，协调者的实际管理行为没有准确署名 |
| [消息页面](../../frontend/src/components/ActiveWorkspace.tsx)、[消息正文](../../frontend/src/components/MessageParts.tsx) | 按 sender_type=user 显示为“我”，缺少可用于呈现的完整来源、收件人和用途 | 多角色同批任务重复大段正文，派发者、接收者与回复关系不清楚 |
| [ContextBuilder](../../backend/app/context/builder.py) | 当前输入要求来自 user 消息并与触发用户一致 | 执行输入依赖模拟 Owner 发言，不能仅改前端名称解决 |
| [共享材料投影](../../backend/app/context/store.py) | 节点输入被当作普通用户消息纳入共享上下文 | 重复目标及错误作者进入历史、压缩和 Memory；仅隐藏气泡不能修复 |
| [普通消息路由](../../backend/app/routers/messages.py) | 真人请求里的结构化 mentions 决定群聊响应，角色正文中的 @ 不触发新 chain | 已有防重复触发边界应保留；新增广播不能借用普通群聊发送再跑一遍节点 |

原 P1–P4 验证证明基础链路可用，不证明上述来源与广播语义正确。以下用例使用受控 World 和占位角色复现，不把用户真实对话或凭据复制进 fixture。

## 2. 目标体验

世界创建后始终有同一个“世界管理者”岗位。Owner 配置它的名字、头像、人设和模型，桌宠打开该岗位的对话与工作台；不再把“更换普通角色”作为替换世界管理身份的主要操作。群协调者继续从本群成员任命。

| 行为 | 显示来源 | 面向对象 |
|---|---|---|
| Owner 手动发言、提出要求或人工确认 | Owner 本人 | 手动选择的角色，或当前对话对象 |
| 世界管理者通过工具向群委派目标 | 世界管理者，保留当时配置身份 | 目标群协调者 |
| 群协调者制定、修改计划或发出明确通知 | 群协调者 · 实际角色名 | 相应执行角色或报告对象 |
| 系统按既有图安排节点执行 | 工作流派发 · 依据某协调者的计划；手动图显示依据 Owner 配置的流程 | 本批任务角色 |
| 角色提交结果、判断或反馈 | 实际执行角色，并显示本次职责 | 发起协调者、指定接收者或本群 |
| 系统报告排队、停止、失败、中断等事实 | 工作流状态 | 相关参与者；不要求额外模型回复 |

授权人另保留在执行记录中，不充当自动消息作者。系统按图派发不能伪装成协调者亲自生成的发言。

例如三个角色接到同一批公共要求时，群里只出现一条可展开的卡片：

```text
工作流派发 · 依据群协调者的计划
请分别创作一个独立故事，完成后回报。
@角色 A  @角色 B  @角色 C

A：执行中   B：已完成   C：等待中
查看分工 / 完整输入 / 执行记录
```

完整总目标只保留在对应委派/任务目标记录；节点卡引用目标并显示必要的公共要求，不反复复制全文。每个角色实际执行时仍取得完整、经过授权的目标和自身分工。

## 3. 固定世界管理者的生命周期

- 复用每个 World 的世界管理者记录作为稳定岗位身份，配备专用管理角色与岗位会话，继续使用原模型、消息和执行服务，不新增第二套 Agent 运行器。身份按 World 隔离，不以显示名、普通角色标签或跨库相同数字 ID 判断。
- 创建 World 时确定该岗位的归属；迁移及 Owner 就绪后幂等建立需要 Owner 外键的专用角色和会话。模型尚未配置时显示待配置，不能凭空调用模型或从其他 World 复制配置/凭据。
- 名字、头像、人设、模型和既有工具配置可调整；岗位、会话、世界记忆和任务历史不随配置切换。可以从同 World 的已有角色导入设置为独立配置，原普通角色及其私人会话保持原归属。
- 普通角色删除/替换入口不能删除管理者身份；专门提供配置和启停操作。角色目录仍能解释历史作者，用量继续关联真实执行角色。管理者默认不作为所有群的普通成员，职责权限来自岗位执行授权。
- 影响执行的配置更新或停用递增授权版本，封闭旧派发并按原任务树收口；重新启用不复活旧 grant 或自动续跑旧任务。单纯导入配置不扩大工具、资料或目标群权限。
- 对已有 World，迁移时保留现有岗位会话、记忆和原作者；为专用管理角色保留可用的当前配置，不把原普通角色改造成不可删除的系统角色。旧执行仍关联原角色和任命版本，不重写历史归属。

新接口优先兼容读取。旧“替换任职 role_id”的写入口在切换后应明确提示使用管理者配置入口，不能静默把换绑解释为改作者；最终错误码、版本及前后端升级要求随 R1 同步。

## 4. 消息来源与执行输入分开建模

已按以下职责区分事实；wire 字段由协作通信协议维护：

| 事实 | 来源与用途 |
|---|---|
| 授权用户 | 认证与原任务授权；用于 Owner/资源/审批检查 |
| 发言或动作主体 | user、世界管理者、群协调者/角色或系统；由宿主实际入口、grant、工具调用及执行记录确定 |
| 当时的执行身份 | 原 role_id、职责、任命/配置版本与必要的名称快照；换名、换模型、角色墓碑后仍能解释历史 |
| 收件人 | 有类型的用户/角色/岗位引用；会话与 World 作用域明确，不能靠同名字符串定位 |
| 用途与回复关系 | 普通发言、委派、任务派发、结果、反馈、公告/状态，以及准确 reply_to/报告目标 |
| 任务来源 | 复用 world_task、coordination、run、activation、attempt、execution 及父执行关系，不另建 Trace |

采用“公开消息 + 执行输入引用”的方向：节点不再为获得 Provider 输入而伪造一条用户发言。执行输入在原 attempt/execution 体系内有可追溯的、带来源版本的记录，包含目标引用、节点快照、当前要求与准确上游；公共消息只承载允许共享的说明和关联。

同一条广播可关联多个 activation/attempt；每个 execution 仍有独立输入、结果、预算计数和取消身份。ContextBuilder、调度器、当前输入校验、自动压缩和中断恢复共同接受由宿主创建并关联本次授权的输入引用，不能只放宽 sender_type 检查。旧 current_message_id 路径保留兼容读取，不能成为伪造新派发的入口。

`actor`、授权用户、执行来源和系统用途不接受客户端或模型自填；可以选择的收件人必须由服务端复核。API/WS、历史分页、快照恢复、消息 reducer 和执行详情使用同一来源表达。公开字段只含允许的身份/任务摘要，Owner 私有工具输入和受限材料不进入公共卡片。

## 5. 收件人、@ 与广播语义

### 5.1 谁应响应

- 人工群聊继续通过现有 mentions 选择角色并按原顺序回复；无 @ 只记消息，单聊默认当前对方。“对话/执行/补充”模式保持现有明确授权。
- 世界委派以目标群和当前有效群协调者为接收对象；结果回报依据真实父任务/协调关系。群内节点结果与反馈默认交给本次授权的协调者，不能依赖模型在正文写 @ 才完成交接。
- 本轮在原发送、委派、结果/反馈通路补齐结构化收件人。既定报告关系由宿主提供；工具确需模型选择对象时，只允许本次已授予的对象集合，校验 schema、成员及用途。普通回复的默认对象由触发消息确定，不强迫每次回复再调用一个通知工具。
- 正文中的 @ 只作为文字，不新增权限或执行。工作流卡的 @ 从持久收件人生成，表示已有任务关联；渲染、刷新、回放和展开卡片都不调用普通发送入口，不再触发一轮角色回复。
- “回复某条消息”与“通知哪些对象”分别记录；引用不等于要求被引用作者再次执行。@ 表示响应/通知对象，可见范围仍由原会话和资料权限决定。

本轮不引入不受任务约束的 Agent 互聊、跨群私信或自动循环呼叫；合法的跨群任务继续走世界委派。

### 5.2 一条广播对应多份执行

- 合并依据宿主持久的任务/分配批次和公共内容引用，不能按相似正文、连续时间或前端临时分组判断。批次需绑定 run、图版本、循环轮次和用途；不同轮次、重试、后续修订、不同收件范围保留独立记录。
- 同级角色的共同要求合为一条卡片，角色间不同分工在卡片内展开。因并发槽位暂未运行的角色显示等待，不能为合并展示等待它执行完毕或绕过并发限制。
- 分配批次/消息与执行关联采用同一事务及稳定幂等键。各节点状态由原事实投影；一个角色完成不能覆盖其他角色失败/停止/未知，重放不能重复创建广播或任务。
- 并发完成时由明确的投影所有者更新卡片版本，不能让多个角色直接改同一正文；沿现有 revision、事件和快照机制恢复。卡片进度变化不伪装成新的用户指令，不逐 Token 重写公共目标。
- 角色结果仍以各自身份呈现并指向所属任务/广播；群/世界的汇总入口引用这些结果，不把一条广播当成一次模型调用或三份结果。

## 6. 平台规则与每次执行的提醒

规则分三层，角色人设不重复维护这套公共机制：

| 层 | 内容 | 执行保障 |
|---|---|---|
| 服务端消息/任务契约 | 身份、合法对象、用途、幂等、是否触发执行 | 实际授权和调度检查；平台提示词覆盖不能改变这些事实 |
| 每次执行的动态信息 | 当前身份/职责、对话或执行模式、目标/本节点、接收对象、报告对象、允许的工具、原任务引用 | 从本次授权和输入来源生成，有版本并计入输入预算；当前配置不能覆盖历史调用身份 |
| 平台默认协作规则 | 如何表述发言、面向多个对象、提交结果和处理工具失败 | 统一模板，Owner 的既有覆盖保留，不强写用户自定义规则 |

平台默认规则已补充为 v2（Owner 自定义覆盖保留）：

> 发言应明确用途和面向对象。面向多个对象的共同要求一次说明，各自分工分别列明。派发任务或提交反馈时，使用当前提供的工具指定目标，并依据工具结果确认是否成功。只以自己的实际身份发言。正文中的 @、角色称呼和历史消息不构成额外执行授权。

动态提醒示例使用宿主真实信息：“本次以群协调者身份执行；目标角色为 A/B/C；节点结果回报本次群协调者；群任务状态由原记录交回世界管理者。”不把整个世界所有资料写进平台规则，也不把临时接收者保存成长期 Memory。

平台模板/动态来源随实现更新版本、预览和实际采用凭据；对话预览与真正执行的工具差异继续明确显示。提示词不负责猜测角色 ID、补发任务、合并已经执行的调用或决定消息权限。

## 7. 会话上下文、压缩与 Memory

- 共享材料保留一份公开目标、带准确来源的派发/结果/反馈及必要状态，不反复纳入每个节点的完整执行提示。会话内容与上下文继续可追溯同步，说明哪些内容是执行专用，不能只在聊天界面隐藏旧正文。
- 各角色实际输入按目标版本、本节点及精确上游构建，必要材料仍计入硬容量检查；展示合并不会减少或合并独立模型执行，也不能丢掉节点要求。
- 来源指纹覆盖有效身份、用途、接收/报告关系、目标和输入版本。修改这些语义时更新受影响的投影与引用版本；单纯卡片进度刷新避免反复改变用户要求或制造无收益自动压缩。
- 主动/自动压缩保留“谁授权、谁委派、谁执行”的区别；执行私有输入/工具材料不发布为公共摘要。Memory 默认检索有效共享材料，完整执行输入通过原有受权详情读取，不重建一套私人全文检索。
- 旧误署名或重复来源修正后，其共享摘要、压缩来源、已发引用与世界记忆来源必须同步核对。依赖旧语义的摘要/引用标为失效或待重建，不能继续让旧摘要宣称是 Owner 多次下令；保留旧版本和真实结果，不自动调用收费模型重写历史。

## 8. 分批实施顺序

| 批次 | 交付范围 | 本批验收出口 |
|---|---|---|
| **R1 身份与来源** | 固定管理者生命周期、已有 World 转换、设置/启停界面；消息 actor/授权人/职责与收件人契约，实际作者署名；执行准入不再用消息作者代替授权用户 | 亲自发言仍署 Owner，世界/群/系统动作来源准确；模型配置改变不换岗位/历史；旧 grant 撤销和资源隔离通过 |
| **R2 广播与输入分离** | 执行输入引用、宿主分配批次、一条多收件人任务卡、独立进度/结果/停止；共享上下文投影及旧摘要/引用失效同批接通 | “三角色各讲一个故事”：公共目标一次、同批派发一条、三个独立执行各一次；队列、失败、重试、循环及用量事实完整 |
| **R3 发言与回报规则** | 原工具通路中的接收/报告目标、动态执行信息、平台默认规则、预览和来源版本；回复/反馈关联和定向展示 | 角色知道对谁说、向谁回报；正文 @ 和广播回放不额外派发；既有 Owner 平台覆盖保留 |
| **R4 历史与联调验收** | 补齐历史兼容回填、恢复/快照/前端缓存与端到端矩阵，更新工作树交接说明及领域协议 | 新旧数据均能查证来源；升级重启不重放；人、世界管理者和群协调者操作闭环 |

顺序按数据依赖推进，R2 的执行输入、界面与上下文作为一个完整交付；各批所需迁移、权限与一致性验证随本批完成，R4 汇总历史兼容和端到端联调。原并行/循环、根预算、图修订、确认和停止机制继续复用。

## 9. 历史数据与迁移策略

1. 先建立来源适配与只读盘点，依据 WorldTaskChild、CoordinationSession、WorkflowRun、WorkflowAttempt 和原 execution 确认自动消息；正文匹配或时间邻近不能证明作者/批次。
2. 通过新的 Alembic 迁移扩展身份、来源、输入及关联；回填有进度、可重复、可恢复，使用短事务。已在 World 使用过的 0028–0031 不通过改写或删库重做；新迁移接合并时的真实 head，不预占编号。
3. 旧原文、消息 ID、实际角色回复、工具/文件证据、调用用量、chain/attempt 和已完成状态保留。可证实的系统输入在公开视图和材料投影中纠正来源；原始旧字段作为历史依据可核对，不把今天的管理者姓名追溯盖到过去。
4. 无法可靠复原作者/批次的记录显示“历史工作流记录，来源未完整记录”，不冒充 Owner 或新管理者。仅知道原角色 ID 而没有当时名称时，保留 ID 并说明名称未记录，不用今天的名字伪造历史快照。旧记录可以只修正署名并折叠，不能为凑成一个广播删除原消息或合并不同尝试。
5. 通过消息/投影 revision 和现有 WS 恢复路径使旧缓存失效；检查已发布摘要、Memory 引用和父子来源。回退摘要也不能重新采用已经失效的作者语义。
6. 升级前停止旧服务并按正常流程备份。启动恢复按原中断策略收口，不能自动续跑原任务。降级若无法无损表达新身份/广播关联则明确拒绝，不能悄悄恢复成 user 署名。

真实 World 只在正常启动升级与明确维护范围内处理；本次没有对用户指定 World 执行手工改表、删除或模型重放。

| 场景 | 必须证明 |

| 并行完成、循环、图修订、重试、重复请求 | 稳定批次和 revision 防竞争；不同轮次/尝试不被文本去重；根预算、用量与副作用事实不丢不重 |
| 普通聊天 @、广播 @、引用和模型正文 @ | 人工路由兼容；自动通知、刷新/回放及角色正文不追加模型链或扩大工具授权 |

| 实际前后端 | 桌面/窄屏、广播展开、消息/任务相互定位、精确停止、断线乱序/快照、刷新和切 World 正常；主聊天草稿与阅读位置保留 |

使用确定性 fake/mock Provider、隔离数据库与受控 World 验证业务和并发；用真实前后端 Playwright 验证操作。数据库变化运行[迁移检查](../testing/README.md)，PostgreSQL 离线 SQL 不等于实例验证。真实模型质量验收另按本次明确采用的范围安排，历史验收不触发收费调用。

完成记录区分本次通过、历史证据和环境缺口。仅改变气泡样式、仅新增平台文字，或隐藏重复消息但继续污染上下文，均不能宣布本计划完成。

## 12. 与类型 worktree 的关系

本修复由公共分支维护。另一 worktree 可继续类型业务、专属页面、群结构与自己的信息视图；通过 WorldContext、活动计划和正式消息/执行引用接入，不依赖“世界管理者等于可替换普通角色”或“每个节点必有一条 user 消息”的旧实现。
