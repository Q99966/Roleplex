## 1. 整改结论与交付目标

整改前已实现群内任命、固定图的模型分配/判断/汇总、并行汇合、显式循环、任务工具分配与资源协调。这些基础继续复用。本阶段在这些基础上扩展图管理，原历史验证与本阶段验收分别记录。

本次补齐的核心是：**协调者读取当前图和约束，通过工具修改图，并在明确授权与版本边界内重规划。** 旧计划没有把这些行为列为具体工具契约和验收条件，不能再用 `workflow_plan/result/summary` 存在或固定图运行通过，宣称群 Orchestrator 已完整实现。

本阶段必须同时完成：

- 无须用户先画完并保存一张可运行图，就能发起本群协调规划，生成可见、可编辑的流程草稿。
- 协调者能读取完整业务结构及必要子图，通过独立的整体写入工具创建/替换目标图，或通过局部编辑工具按稳定 ID 增删节点、重接连线、修改输入、条件、循环和任务分配。
- 前端画布与模型通过同一图编辑服务修改定义，修改立即可见且不会静默覆盖对方的新版本。
- 运行中能观察真实状态，修改尚未派发的部分或未来循环轮次；已有执行、文件提交与历史结果保留原关联。
- 任命、协调会话、执行授权、图可编辑范围和每次工具调用的复核规则明确，正常工作角色不获得图管理能力。

范围仍限当前群。世界 Orchestrator、桌宠 API、跨群派发、Git/worktree 和新的统一时间/费用限额不作为前置。现有非嵌套循环等支持范围不因本次图编辑整改自动扩大。

## 2. 实施前结构与修正位置

当前图是 `WorkflowDefinition.graph` 中的 JSON：`nodes`、`edges`、`entries`、`edge_rules`、`loops`、`concurrency` 和 `runtime_version`。启动时编译为 `WorkflowRun.snapshot`，派生 `order/incoming/outgoing/loop_membership`；运行事实由 activation、attempt、execution 和 allocation 记录。React Flow 是该 JSON 的编辑/展示视图。

以下是本阶段采用并实现的修正项；实际接口和支持边界以工作流协议为准：

| 编号 | 实施前问题与代码位置 | 修正与完成条件 |
|---|---|---|
| R1 协调入口 | [engine.py](../../backend/app/workflows/engine.py) 先读取定义并 `compile_graph`、冻结快照，再创建 `__plan`；前端 [WorkflowContext.tsx](../../frontend/src/components/workflows/WorkflowContext.tsx) 也要求先保存才能启动 | 将 `/plan@协调者 <目标或调整要求>` 作为明确的规划入口，与运行启动分开。允许目标定义为空或仍是不可运行草稿；只有发布/启动时要求执行语义完整。 |
| R2 图操作能力 | [coordination.py](../../backend/app/workflows/coordination.py) 的 `workflow_plan` 只能给全部已有 role/judge 节点提交 assignment，不能改变图 | 增加读图、独立整体写入、语义化批量编辑和运行检查工具，支持真实节点/连线/条件/循环变化；不能只包装原 assignment 接口。 |
| R3 授权表达 | 控制工具由 `names_for(attempt.phase)` 自动拼接；[allocations.py](../../backend/app/workflows/allocations.py) 的 `tools_json` 主要表达工作区工具 | 协调工具能力显式进入本次授权；工具可见性、上下文策略和执行检查共用一份计算结果。未知职责/能力默认不授予，不能落入“其他 phase 都能上报”的默认分支。 |
| R4 工具说明与结果 | 控制参数说明不完整；规划输入只给节点部分字段和工具名称；结果 schema 只有通用标量字典，提交一次后不能调整 | 返回实际图结构、可编辑范围、合法角色/工具及限制；参数逐项说明，错误定位到操作/节点；结果 schema 按节点要求说明类型，非法结果允许在原预算内修正。 |
| R5 共享编辑入口 | [service.py](../../backend/app/workflows/service.py) 保存整份 graph；模型没有调用路径；前端在 `changeGraph` 中自行维护部分引用 | 新增统一图编辑服务，前端/Agent/兼容 REST 共用验证和提交逻辑。整图保存保留必要兼容；模型分别通过 workflow_write_graph 整体写入和 workflow_edit_graph 按 ID 局部编辑，二者共用后台校验与提交逻辑。 |
| R6 图版本与运行版本 | 定义 revision 与运行 snapshot 分开，但没有运行图修订及适用区域；运行 revision 还随进度变化 | 明确草稿/定义版本与运行图版本。进度更新不无谓冲突图编辑；每次激活绑定所用图版本，旧定义/旧运行可读，不伪造历史版本。 |
| R7 运行中重规划 | [engine.py](../../backend/app/workflows/engine.py) 消费固定快照和启动时创建的激活；`plan → work → summary` 无改图入口 | 在安全调度边界应用新运行图版本，重算待执行依赖，处理新增/移除的未执行节点及未来轮次。禁止原地覆盖活跃任务的输入和授权。 |
| R8 编译与引用一致性 | [graph.py](../../backend/app/workflows/graph.py) 的编译检查在启动边界；节点、边、edge_rules、inputs、condition.sources 和 loops 分散引用 | 每批编辑检查结构/引用；发布及运行变更做完整编译，重新生成派生索引。删除、重接、循环变更不能留下悬空引用或静默改变用户要求。 |
| R9 画布与事件 | [WorkflowFlow.tsx](../../frontend/src/components/workflows/WorkflowFlow.tsx)、[前端 API](../../frontend/src/api/workflows.ts) 只处理人工定义编辑/运行快照 | 模型修改经服务端提交后进入同一画布；显示新增/删除/修改及版本，未保存人工草稿遇到变化明确冲突；保持布局、对话草稿、选中项和连接。 |
| R10 完成口径与测试 | 现有[测试记录](../testing/orchestrator-v2.md)证明预设图的分配与运行，不证明模型编辑图 | 增加从目标创建图、工具修改图、运行中重规划和授权生命周期的端到端用例；修正“群级完整完成”的说明，同时保留原测试事实。 |

修改不能让模型直接写数据库、改后端源码、操纵 React Flow 内部状态或使用前端 Owner Token 绕过执行层。

## 3. 任命、协调会话与工具授权

任命表示角色有资格承接本群协调任务，不表示所有发言永久获得图管理工具。Owner 的本次请求建立协调会话，可先没有 workflow run；模型执行绑定该会话与具体目标。

| 场景 | 授予时机与范围 |
|---|---|
| 未任命，或普通聊天/普通 `@` | 不获得群图管理工具。任命本身不偷偷改变普通消息路由。 |
| Owner 通过 `/plan@协调者 <要求>` 发起规划/调整 | 创建协调会话，绑定当前群、任命版本和可选目标定义；授予目标草稿的读/整体写入/局部编辑/校验能力，不授予启动权。无图时可创建草稿，不要求先有可运行图。 |
| Owner 发起“协调执行” | 同样允许规划和编辑，并记录本次已授权的启动范围；合法图就绪后可启动，不再为已经授权的每次正常编辑重复要求人工确认。 |
| Owner 调整运行，或运行进入已授权的重规划处理点 | 创建新的协调执行，授予目标运行的观察及受控重规划能力；可以读取旧结果，编辑范围由当前状态与授权共同确定，不复用旧模型执行状态。 |
| 普通工作/判断节点，包括恰好使用协调者角色 | 只获得本次任务工具，以及任务确实需要的结构化结果上报能力；不继承图编辑或群级分派权。 |
| 任命更换/撤销、角色移出/停用、请求取消或作用域失效 | 封闭对应协调执行的后续修改/派发；每次工具调用和提交前复核，即使旧工具对象仍在内存也拒绝。保留已提交的图变更与执行事实。 |

规划命令的入口约定：

- 在群聊输入框中使用 `/plan@协调者 帮我设计开发—审查流程`；`@协调者` 通过已有角色选择器解析为稳定角色 ID，并非必须名为“协调者”的角色。
- 前端将命令解析为明确的规划请求，后端独立验证 Owner、本群成员及当前任命。任命缺失、对象不是当前协调者或请求无效时给出明确错误，不静默退回普通聊天或猜测接收者。普通 `@` 保持原路由；引用或正文中出现命令文字不构成授权。
- 未选择目标流程时创建新草稿；已选择定义/草稿时调整该对象，发送前显示目标，后端绑定准确 ID 和版本。不能依据模型猜测或其他窗口的选中状态决定覆盖哪张图。已有未保存人工编辑仍遵守冲突保护，不会被规划请求静默丢弃。
- `/plan` 只授予设计能力。即使目标文字含“执行”，也不能越过本次能力范围启动；启动沿用另行明确授权的“协调执行”入口。选中运行时不能把 `/plan` 隐式升级为运行重规划，应显式选择目标定义，或使用“调整运行”入口。

授权上下文由后台建立，至少关联 Owner、conversation、协调角色、任命版本、协调会话/执行、目标 definition/run、允许能力、资源范围及授权修订。模型参数不能覆盖这些身份或任意跳到其他群。图管理与工作区工具复用共同的授权检查入口，避免维护两套相互矛盾的过滤规则。

实施前 `ExecutionAllocation.attempt_id` 依赖已有工作流尝试；现已增加独立 CoordinationSession、可空 attempt_id 及明确 control_tools_json，并提供迁移。不能为满足旧外键而偷偷创建伪造的已启动流程、默认任务图或已完成节点。协调会话可以多次读图/编辑/检查，图修改不能继续受 `attempt.result_json` 一次性上报门槛限制。

授予条件在模型请求前决定工具可见性，在工具调用及提交时再次校验；资源忙、版本冲突和撤权分别反馈。图编辑不授予工作区访问，也不允许扩大角色的全局工具配置。

协调会话及后续工作流沿用现有链路与共享预算归属。规划发生在 run 创建之前时，也要先有可追踪的请求/执行和预算；创建 run、图修订、重新规划或进入循环不重置已消费额度。模型调用、图工具动作与工作节点耗时/usage 分别记录，usage 仍只取厂商报告。

## 4. 模型工具与语义操作

以下能力已接入；具体字段、导出 schema 和兼容规则见[工作流协议](../protocol/public/rest/workflows.md#图工具与统一提交)。

| 工具/能力 | 输入与返回要求 |
|---|---|
| `workflow_read_graph` | 读取授权定义/运行图及版本，可按节点或关联子图取数据；返回节点、连线、输入引用、条件、循环、合法成员/工具、编译问题和当前不可修改部分。结果不完整时明确覆盖范围及续读方式。 |
| `workflow_write_graph` | 接受目标图期望版本、幂等修改键和完整 graph，创建新草稿或整体替换授权目标图；支持只校验和提交。返回新版本、实际差异、受影响节点/引用及是否可执行；失败定位到字段/节点，不回显敏感输入。运行图替换须具备明确重规划授权并遵守第 5 节的冻结边界。 |
| `workflow_edit_graph` | 仅接受目标图期望版本、幂等修改键和带类型的局部操作批次；支持只校验和提交。返回新版本、实际变更、受影响节点/引用及是否可执行；失败定位到具体操作，不回显敏感输入。 |
| `workflow_inspect_run` | 读取目标运行的节点/轮次/尝试、结果引用、等待/受阻原因和当前图版本。复用准确工具/文件事实，不从模型正文或日志猜测。 |
| 运行启动/控制适配 | 在本次授权内复用启动、停止、重试和继续语义；与编辑显式分开，保存图不自动启动。人工确认及工具审批继续使用 Owner 入口，模型不能代签。 |
| `workflow_result` | 作为当前工作节点的结果报告能力保留；参数帮助和 schema 描述该节点必需字段及类型。错误报告允许修正，重复提交有明确幂等语义，已被下游消费的结果不可静默改写。 |
| 旧 `workflow_plan` / `workflow_summary` | 保留必要的旧运行兼容；plan 不能再承担“完整图规划已完成”的证明。汇总提交不代替观察/重规划能力，也不能改变真实运行终态。 |

`workflow_write_graph` 与 `workflow_edit_graph` 是两个独立的模型工具，不在 edit 中混入 `graph` / `operations` 双模式。write 适合从目标生成完整图或整体重构，edit 适合局部修订；底层仍保存 JSON，二者共享同一授权、版本、幂等、校验及提交服务。

整体写入的契约：

- `graph` 是目标图的完整业务结构，使用明确 schema，不接受任意数据库字段、执行身份/状态或编译派生索引。整体替换不隐式合并被遗漏的业务节点和连线；遗漏已有节点意味着请求删除，必须受删除权限、保护条件及运行状态限制。读图只返回子图或不完整数据时，不能把该片段误作整图覆盖。
- 新图在本次授权的新草稿槽位中创建，约定 `expected_graph_revision=0` 表示尚不存在；创建与修改身份持久去重，重复调用不能多建定义。已有目标必须携带准确图版本，不能通过改目标 ID 或使用 0 强行覆盖。
- 按稳定 ID 计算整体差异，保留未改业务节点的 ID、历史关联及已有布局/颜色；已有节点未提供展示字段时沿用其展示值，显式更新才改变。不能把整图写入实现为删除所有节点再重建，也不能借整体替换规避活跃任务冻结、人工确认或资源/工具权限。
- write 与 edit 都支持只校验、不提交的模式；提交时重新校验最新版本与权限。只有设计权的会话可创建/替换草稿，不能修改正在运行的图；运行图整体写入需单独具备该运行的重规划能力。
- 两个工具的幂等记录共用目标图的修改键空间，并将工具名及规范化请求内容纳入摘要。同键同请求返回原结果；同键不同正文或换用另一工具明确冲突。整体写入同样全成或全败，保存不自动启动。

`workflow_edit_graph` 用带判别字段的结构化操作，不能是任意 dict 或只接受自然语言的“帮我改图”。最小操作集合：

| 操作 | 语义 |
|---|---|
| `add_node` / `update_node` / `remove_node` | 按稳定 node_id 处理节点及允许编辑的设计字段；role_id/tools 仍受群成员与授权限制，不能写入执行状态或身份字段。 |
| `connect` / `disconnect` | 按 source/target 维护连线及对应条件规则；不依赖数组下标，也不只改 edges 而遗漏 edge_rules。 |
| `set_inputs` | 明确更新节点消费的上游结果；与控制依赖分开检查，不能默认连接一条边就暴露所有上游私有详情。 |
| `set_condition` | 设置结构化判断规则，并验证来源、结果类型和对应出边。 |
| `upsert_loop` / `remove_loop` | 原子处理循环声明及相关引用；遵守当前循环执行能力，不用普通连线猜测回边语义。 |
| `set_entries` / 并发配置调整 | 显式处理入口与主机允许范围内的并发配置；不扩大本次资源、工具或预算授权。 |

节点 ID 与编辑语义是模型接口，底层仍可保留 nodes 数组的 JSON 存储。位置/颜色等展示字段按需编辑，业务结构变动不重置用户布局。通用 JSON Patch 可以用于内部实现，但不直接要求模型操作 `/nodes/3` 这类易随重排变化的地址。

整体写入先在副本上构造目标图及按 ID 的差异，局部编辑在副本上应用操作；两者均按“读取期望版本 → 在副本上应用完整变更 → 校验 → 短事务内复核并原子提交”处理。同一批可以先断开旧边再接新节点，不要求中间每一步都可运行；最终引用有效，任何失败均不留下半批修改。

例如通过 `workflow_edit_graph` 在已授权的普通并行流程中追加审查节点，假设 develop/review/merge 已存在：

```json
{
  "expected_graph_revision": 12,
  "mutation_key": "add-review-001",
  "operations": [
    {"op":"add_node","node":{"id":"security_review","kind":"role","title":"安全审查","role_id":3,"task":"检查上游修改的安全问题","inputs":["develop"],"tools":["workspace_read"]}},
    {"op":"connect","source":"develop","target":"security_review","when":"always"},
    {"op":"connect","source":"security_review","target":"merge","when":"always"},
    {"op":"set_inputs","node_id":"merge","inputs":["review","security_review"]}
  ]
}
```

该示例使用当前工具参数的占位数据；具体目标由协调授权绑定。若节点位于循环域，同批还需声明相应循环调整；校验返回具体缺口，不能静默把节点放到错误轮次。

工具说明必须覆盖参数用途、ID 来源、允许/禁止修改的部分、版本和幂等、返回数据、错误后的修正方法，并提供与实际导出 schema 一致的示例。合法成员和可用工具需要名称、用途与必要参数信息，不能只有不可解释的 ID/工具名；凭据和完整私有配置不进入模型或工具说明。

## 5. 图版本、校验与运行中修改

**定义版本与运行图版本分开管理。** 修改定义影响后续启动；修改正在运行的流程通过明确的运行重规划操作创建新图版本。运行进度 revision、图版本与任命版本分别表达不同冲突，不能因普通节点进度更新让每次编辑都失败。

- 草稿保存允许尚未连接完整的流程，校验结构、引用与权限；发布/启动、运行图修订使用完整编译。编译派生的 order/incoming/outgoing 等只由后台生成，不能让模型直接写入。
- 每次成功编辑持久保存修改身份、来源执行、基于的图版本、新版本和必要变更记录。相同幂等键与相同内容返回同一次结果，不同内容冲突；不能仅用内存去重。
- 定义、运行图与相关迁移需保留旧读取兼容；具体新表/字段在数据模型文档定稿。没有历史版本的数据明确为旧记录，不倒推或伪造当时图版本。
- 用户明确要求固定的角色、审批步骤、工具或资源属于保护条件；可编辑范围应随读图返回。其他已授权设计字段不能仅因过去填过值就被永久禁止修改。

运行重规划的边界如下：

| 部分 | 处理方式 |
|---|---|
| 完全未派发的节点/依赖 | 可增删改并重新计算就绪条件，旧的待执行意图保留修订关联，不伪造成已执行。 |
| 已入队或正在执行的尝试 | 输入、角色、工具分配和所用图版本保持冻结。确需改变时先明确取消并确认收口，再创建新尝试，不能就地改写 QueueJob 或 allocation。 |
| 已完成/失败/停止的尝试 | 保留原图版本、输入和副作用事实；可作为新增后继的明确来源，不强制重跑已完成节点。改图不能将旧失败改成成功。 |
| 从已完成/活跃节点新增后继 | 可以表达未来依赖；不会修改该来源节点已冻结的执行内容。后继只在来源真实结果已交接且依赖有效时派发。 |
| 循环 | 当前已激活轮次保持精确版本；未来轮次可采用显式的新修订，不混用旧成功、旧判断或其他轮次尝试。改变作用域/回边必须在明确的循环边界应用。 |

重规划提交时短暂封闭受影响子图的新派发，复核最新状态、权限和版本，原子保存新图/适用范围/依赖并恢复调度；校验失败原图继续有效，无关分支不必停止。停止与改图竞争时，已停止运行不能被迟到编辑重新启动。

所有激活/尝试能追溯所用图版本及准确上游版本。移除未执行分支时处理汇合等待，改变条件/循环时重建必要索引；不能让新节点永久没有 activation、汇合死等旧边或重复派发已经执行的操作。

## 6. 前端同步与具体修正清单

- 输入框支持 `/plan` 命令及现有角色选择器，显示规划目标与仅设计权限；命令提交、后端模式及工具实际授予保持一致。
- `WorkflowContext`、画布节点/连线表单与 workflow_write_graph/workflow_edit_graph 共用后台编辑服务。前端可提供即时预览，但不另造一套循环/依赖修复规则；原整图 PUT 通过相同验证边界保留兼容。
- 保存成功后通过服务端版本通知/快照更新画布。定义修改与运行图修订标明对象，不让用户在运行视图误以为已修改模板，或在模板视图误以为运行已更新。
- 模型修改与人工未保存草稿并存时显示冲突和可核对的变更；不直接刷新掉用户编辑。仅布局变化不重排业务执行顺序。
- 图工具结果能关联到协调者的具体修改、节点和运行版本。查看历史时呈现当时图与尝试，不能只把所有历史状态叠到最新图上。
- 前端保留已实现的覆盖主聊天区、返回对话、草稿/阅读位置、键盘操作与断线恢复；本阶段不重做画布选型。
- `coordination.py` / `allocations.py` / ContextBuilder / 工具工厂同步采用本次授权。不能只新增工具函数却没有规划入口，或只改提示词却保留“必须先完整保存并启动”的前置。
- 图编辑接口、模型工具、数据模型、错误码、消息/WS 提示和诊断记录随实现同步。修改正文与任务内容属于业务数据，日志仅保留允许的变更身份、版本、计数和安全原因。

## 7. 实施顺序与验收

1. **协调入口与授权上下文**：通过 `/plan@协调者` 从目标或现有草稿进入，明确普通消息、设计请求、协调执行和运行调整的能力范围；补齐任命/撤销竞争与预算归属。
2. **统一读图、写图和编辑服务**：实现独立整体写入工具与按 ID 局部编辑工具、草稿/执行校验、版本与幂等，以及前端与模型共同调用；完成从目标生成图及修改现有图。
3. **运行图修订与重规划**：实现图版本、激活关联、受影响子图的安全提交、循环适用边界和停止竞争，保留已执行事实。
4. **完整模型与浏览器闭环**：接入模型可理解的 schema/说明/错误反馈、画布变更展示与真实群协调验证。以上一起构成本阶段完成，不再以固定图上报路径代替验收。

| 验收场景 | 必须观察到的结果 |
|---|---|
| 无现成可运行图 | Owner 通过 `/plan@协调者` 只给目标或未完成草稿，协调者实际读能力并调用图工具创建/完善图；不要求用户先画出最终结构，不直接由测试脚本预置最终图冒充。 |
| 整体写入与局部编辑 | 模型实际调用 workflow_write_graph 创建完整草稿、整体替换已有授权草稿，再通过 workflow_edit_graph 局部调整；两个工具职责独立。整体遗漏业务节点按删除校验，保留稳定 ID/布局/历史，部分读图不能误作整图覆盖。 |
| 修改结构与引用 | 协调者新增/更新/删除节点、重接连线、修改 inputs/条件/循环；画布与存储一致。无效引用/角色/条件返回可定位错误，合法修正后成功。 |
| 前端与模型共同编辑 | 人工保存、模型 write/edit 同时基于旧版本修改只有一个原子提交成功；另一个收到冲突并可重读修正，未保存布局和任务不会无提示丢失。 |
| 幂等和原子性 | 整体写入或局部编辑的网络重发、工具重试和响应丢失不重复建图/添加节点；无效整图或批次任一步无效均不保存部分修改；重复键不同内容或跨工具复用明确拒绝，只校验模式不产生业务修改。 |
| 运行中新增审查 | 在开发节点已完成或正在执行时新增审查及汇合依赖，新节点真实派发；已完成开发不重跑，运行中输入不被改写，修改后节点/文件事实与图版本可追踪。 |
| 并行与循环重规划 | 多分支运行时调整未派发子图，无关分支继续；未来轮次使用新版本，当前轮和旧结果保留；无死等、串轮、重复回边或对已提交文件的盲重放。 |
| 工具授予与撤销 | 任命后的普通发言、普通工作节点不获图管理权；有效协调请求在 run 尚不存在时能获草稿编辑权；换任命、停止、跨群/World、失效目标及旧工具对象不能越权修改。 |
| 规划命令与范围边界 | `/plan` 正确解析角色与显式目标；未任命、非当前协调者、Guest 和正文引用命令不能获得管理权。只有设计权不能启动流程或整体覆盖运行图；保存不隐式启动；图编辑不能扩大角色工具、资源或预算，不绕过 Owner 人工确认/工具审批。 |
| 恢复与历史 | 刷新、断线、重复/乱序通知、进程重启恢复正确版本和修改记录；不自动重放图提交或工具副作用，不把最新图冒充旧尝试的执行图。 |
| 真实 Provider | 沿用标准真实 World 入口，协调者实际调用图编辑工具创建或调整流程，画布可查看变更及后续真实执行结果；并发竞争、恶意参数和精确边界使用 fake/确定性测试。 |

扩展现有 `backend/tests/test_orchestrator.py`、`test_workflows.py` 及工作流浏览器场景，图编辑服务另补有意义的单元/集成覆盖；schema 变化执行 Alembic SQLite 重放与 PostgreSQL 离线编译。命令、数据隔离、保留与真实凭据规则统一见[测试指南](../testing/README.md)，新入口已登记在测试指南。

真实 Provider 属于该功能的实现验收：推进实现时先说明联网计费，再使用独立命令验证并保留可查看 World；本阶段已按该入口运行真实图管理验收，不将旧固定图测试当作本次整改完成。

## 8. 完成口径

只有“目标/草稿 → 明确授权的协调执行 → 实际图工具修改 → 版本化提交与画布同步 → 启动或运行重规划 → 准确结果/历史”闭环通过上述成功与关键失败路径，才将本整改标为完成。

协议入口与 README 分别维护当前可用能力和未实现项；旧计划保留基础实现记录并链接本计划，历史测试报告保留原结果与覆盖边界。新增工具的参数和状态以实施后的领域协议为准，本文不提前宣称新 API 可用。
