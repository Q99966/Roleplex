## 二补、G：工具职责与编辑路径关口

### G.1 已确认的方向与实施边界

单有可信 diff 不保证日常可见：如果更方便的修改入口是服务脚本，或服务运行使正规编辑入口不可用，
只覆盖 write 的页面会长期缺少记录。应降低正常编辑的成本，并如实表达其他入口的能力，而非要求模型把每个工具用一遍。

现有 W1d 明确要求逐次审批完整脚本、cwd、端口、探针与寿命，并冻结审批计划；不能未经检查就说界面隐藏了脚本。
服务存续期间拒绝原生写入是保留冲突边界、暂不承诺 HMR 的保守策略；允许已审批 Shell 后，它不再形成一致的文件写入隔离。
G 按以下方向细化验收并复核权威协议，不只修改工具描述，也不直接删除运行态检查：

| 决策 | 建议方向 | 实施前必须明确 |
|---|---|---|
| 局部编辑入口 | 将最小 `workspace_edit` 提前为 E | 精确匹配、hash、授权、运行占用策略、失败语义与 diff 复用 |
| 服务运行中编辑 | 已批准：停止 → 编辑 → 重新审批启动 | 涉及其他会话服务由 Owner 协调，不得擅自代停；清理未确认不得编辑 |
| 服务启动入口 | 已确认保留通用脚本与工具自由度 | 共同授权、完整审批、独立托管与覆盖缺口明确可验证 |

用户已撤回强制收窄要求。本版替换历史收窄候选：不撤下 script，不增加固定启动器/项目入口白名单，
不通过禁止换行、`&&`、特定命令名或解释器参数来宣称隔离任意脚本副作用。
服务仍限现行已批准的 Linux HTTP 开发服务范围；“保留自由度”不扩展为通用守护进程、Docker 托管或跨平台沙箱。

### G.1.1 工具职责与共同授权

| 路径 | 主要用途 | 执行约束与变化记录 |
|---|---|---|
| workspace_write / 后续 workspace_edit | 创建、整文件替换 / 精确局部修改 | 原生路径与 hash 校验；停服编辑；D/E 提供调用级 diff |
| workspace_run_command | 当前固定 pwd/list/read/count | 保留固定能力集，不能自动扩展成任意命令；未来扩展按真实副作用评审 |
| workspace_run_shell | 一次性复杂命令、安装、测试、构建、格式化、生成器 | 任意脚本、逐次审批、调用结束清理；不承诺文件变化已采集 |
| workspace_start_service | 将获准脚本启动的 HTTP 开发服务持续托管 | 任意脚本、逐次审批，额外受配额、就绪、寿命和回收约束；不承诺文件变化已采集 |

已有 `workspaces/tools.py` 共用部分执行授权，runtime 启动复用审批链路；G 首先画出实际调用链和规则矩阵，
复用已有实现，不另造通用策略 DSL、第二套审批或审计身份。相同事实只保留一个规则来源，生命周期相关复核仍放在实际执行关口。

- **共同安全事实：** 当前 World/Owner、会话成员与角色归属、有效 execution/generation、工作区绑定/lease、
  角色和工作区配置、取消状态、批量清理及未确认回收；在各自适用的申请、决定、预留和 spawn 关口复核。
  后台服务 ready 后使用已登记的服务身份管理，不要求已完成的 generation 永远保持 running。
- **能力开关保持独立：** 禁用某个 Shell 工具不自动撤销独立开启的服务能力，也不把开启 Shell 视为允许服务。
  共同授权拒绝不可绕过；具体工具未启用则该工具拒绝。若未来需要“一键禁用全部代码执行”，另行设计总开关，
  不能在本轮默默改变现有配置含义。
- **审批不可替换：** 审批绑定实际脚本、工具类别、调用身份、工作区及服务参数；不得复用、篡改或移用已拒绝/过期的批准。
  Owner 拒绝一次请求不等于永久封禁所有语义相近脚本；模型必须尊重拒绝，不自动换工具重试同一意图。
  后端可证明身份和批准不能移用，不能证明任意改写后的程序语义等价；不通过脚本 hash 黑名单冒充此能力。
- **完整可见：** 审批展示完整脚本及实际运行上下文，服务参数与普通 Shell 的区别清楚可见。
  明确脚本可能读写文件、访问网络和产生外部副作用；审批不冻结其读取的全部文件与依赖，不宣称脚本未变就代表行为未变。
- **环境与生命周期：** 保持受控环境、凭据保护、三层配额、端口、取消/超时、HTTP 就绪和进程树回收；
  服务增加托管职责而不是减少执行检查。启动失败、停止成功或回收确认都不能表述为文件/外部系统已经回滚。

### G.1.2 模型工作流与前端说明

- 普通源码创建优先 write，局部修改优先 edit；安装、格式化、批量生成等操作可以使用脚本，不强求调用数量或工具覆盖率。
- 服务脚本可以包含必要的准备操作，不为整理工具分工而拒绝已获准的合法组合；不要仅为减少调用次数把普通源码编辑塞进启动脚本。
- 原生编辑因服务占用被拒绝时，按停服流程协调；不要自动用 Shell/服务规避该拒绝。此项属于工作流引导，
  不改变 Owner 仍可明确批准有文件副作用的脚本这一现实边界，也不声称已阻止所有间接写入。
- 工具描述/系统提示只引用当前真正可用的能力；E 未实现或角色未启用 edit 时，不能引导调用不存在的工具。
  提示词、工具 schema 或策略内容变化必须同步既有版本/指纹，不引入随机上下文，不记录 Prompt 原文。
- 工具名称保持前后端一致。Shell/服务卡明确“未采集文件差异，不代表没有修改”，不能把未采集显示成“无变化”。
  只增加必要的能力说明，不重复堆放每张卡的大段警告；Owner 私有脚本仍通过受保护详情读取，Guest 不获得正文。
- 共同规则若现有代码已经满足，只补证据与回归，不为“统一”重写整个运行器。若有缺口，先同步对应 W1d/协议规则再修复，
  不改现有 script 请求格式、不迁移历史审批、不重新执行旧请求，也不借改造额外停止正在运行的实例。

### G.2 最小局部编辑候选

用户已确认工具名保持前后端一致，保留 `workspace_` 前缀，便于追踪问题；本轮不实施显示别名或协议改名。
未知/MCP 工具同样保留可辨识名称。将来若另行决定改名，须同步工具注册、配置、执行权限、详情采集、历史兼容、策略指纹和测试。

E1 已按 `workspace_edit(path, old_text, new_text, expected_sha256)` 实现，字段与错误码见工作区领域协议：

- 只修改已有 UTF-8 普通文件；old_text 非空，按字面精确匹配，包含重叠候选在内必须恰有一处，否则拒绝且不写文件。
- 不做正则、模糊匹配、自动缩进修复或自动全局替换；new_text 可为空以删除片段，但不删除文件。
- expected hash 必填，校验完整文件版本；同一份已读取、校验内容完成匹配和新内容构造，不通过额外无保护的读写拼接。
- G 定稿需核查 read → edit 闭环：现有 read 分段结果已含全文件 SHA-256，优先复用；确认模型实际收到的结果
  保留该 hash，不能只看文件服务返回类型。片段与 hash 必须来自同次读取的同一版本；跨页读取期间 hash 改变时
  不得拼接不同版本或使用片段 hash 冒充全文件 hash。旧版本在 edit 时应明确冲突，不能由模型猜 hash 或服务端静默补最新值。
- 沿用 write 的路径、敏感内容、大小、授权、运行占用及提交前复核；所有实际写入复用共同受控写路径，不能复制出第二套安全实现。
- 输入片段有字节上限，结果文件仍受 1 MiB 限制；G 定稿预算时覆盖大文件小修改场景。
- E1 沿用已批准建议：old_text/new_text 的 UTF-8 合计上限为 64 KiB；schema 每片段最多 65536 字符、路径最多 1024 字符，
  实际字节上限在执行层校验，不用字符数代替字节数。大文件允许只传小片段及全文件 hash，不要求把整个文件复制进 edit 请求。
- 复用执行处前后证据和 Owner diff。不可仅把 old_text/new_text 当成已成功修改；失败、不变及结果未知均沿用 D 的语义。
- E 是 managed_directory 的单文件字面替换，不提前开放 W3 的 Git worktree、多文件补丁或删除能力。

### G.3 服务占用下的正规工作流

本轮已批准采用停服编辑：工具拒绝须说明需要停止阻塞编辑的托管服务，Owner 通过现有授权流程协调；
确认相关占用释放后 edit/write，再以新审批启动。停止一个服务不代表同工作区其他服务均已结束，
不能自动停止其他会话服务，也不保证外部编辑器和非托管进程停止写入。

若用户选择运行中原生编辑，必须单独设计服务启动/停止与编辑的竞争、文件版本、服务就绪状态和清理门槛，
更新 W1d 计划并明确验收；不能只删除占用判断。本草案不预先批准 HMR 或运行中编辑。

用户提出未来可由 Agent 临时拉起群聊，协商哪些服务需要停止以便修改；本轮只记录为后续方向，不实现自动建群、
跨会话协商或新的停止权限。当前受其他会话服务阻塞时，应报告原因并等待 Owner 协调，不自动批量停服。
未来即使协商达成一致，仍须由服务端按服务归属、授权和实时状态执行；聊天中的同意不自动产生跨会话控制权，
也不代替重新启动的 Owner 审批。该能力待相关 Agent/群聊架构阶段另行设计与验收。

### G.4 两类变更记录不混用

- **工具编辑记录：** 本次 write/edit 确认提交的前后变化，放在原工具卡；D/E 交付。
- **工作区观察记录：** 某个明确基线与检查点之间观察到的净变化，可能混合 Shell、服务、人工和其他会话写入；后续设计。

后者必须标明时间/基线、范围、忽略项、不完整情况及来源未精确归属；不能从服务启动调用返回推断后续文件变化结束，
也不能把区间净变化命名为某工具完整审计。本轮不增加扫描器、快照或观察记录接口。

### G.5 实施步骤与阶段出口（已授权实施，验收状态见文首）

#### G0：规则矩阵与基线

- 从工具暴露、执行授权、人工审批、runtime 预留/spawn 和管理接口反查现有规则，列出每项事实来源、
  哪些入口适用、复核时机、拒绝语义与对应测试；特别检查 ready 前后身份转移，不把调用级状态错用于存续服务。
- 明确三类区别：共同资源/安全拒绝、单个工具能力关闭、Owner 对一次请求的拒绝；不能把三者混为全局脚本封禁。
- 交付矩阵及实际缺口清单。没有缺口可以直接记录通过；涉及新权限、总开关或不兼容变化须先回到用户确认，不擅自扩大 G。

#### G1：必要的共同规则补齐与工作流说明

- 先用确定性测试证明缺口，再最小化修复；优先复用已有授权/审批实现，保持各工具独立开关和安全摘要规则。
- 同步模型工具说明、稳定提示词/指纹及前端审批/覆盖提示，确保启动服务不被表述为只读或无其他副作用。
- pytest/集成矩阵至少覆盖 Owner/Guest、跨会话/工作区、角色或开关撤销、generation 取消、审批内容篡改/移用、
  配额预留竞争、清理待确认、World 关闭、审批后 spawn 前状态变化、ready 后管理不依赖存活 generation。
- fake Provider 明确构造失败后换入口、脚本合法包含准备操作、服务运行中原生写入拒绝等情况：
  共同拒绝在适用入口一致生效；新的独立审批不被当作原请求自动授权；合法组合不能仅因包含写文件操作而被额外禁止。
- 浏览器真实前后端验证完整脚本审批、Owner 拒绝/Guest 无权、覆盖缺口提示，以及停服/编辑/重新审批启动的可继续流程。
  若 G1 有产品改动，保留成功与失败路径、受控截图并独立交用户验收/提交，不夹带 D/E 或未来运行中编辑。

#### G2：现成 diff 库的小规模选型验证

- 优先复用库，不从零实现 diff 算法或整套渲染器。候选为 Python 标准库
  [difflib](https://docs.python.org/3.12/library/difflib.html) 与前端
  [react-diff-view](https://github.com/otakustay/react-diff-view)；
  [jsdiff](https://github.com/kpdecker/jsdiff) 作为备选，不能为接入 JS 算法就默认增加产品 Node 后端进程。
- 查验许可证、选定发布版本、React/TypeScript 兼容、依赖体积及维护情况；候选不是已选依赖。
  仅在独立试验目录验证，先不改产品依赖锁文件，不将第三方 hunk 对象直接定为项目公开协议。
- 比较计算与显示两层：后端从已确认的前后内容生成有界结构化记录，前端只显示获授权的记录；
  不为使用某个浏览器库而向前端额外发送两份完整源文件，不依赖当前 Git HEAD 或落地明文临时快照。
- 样本包括新建/空文件/不变、中文和 emoji、LF/CRLF/无末尾换行、130 KiB 文件改三行、接近 1 MiB 文件的小改、
  高重复行、全量替换、超长单行、HTML/终端控制字符以及超出保留预算的结果。
- 分开报告读取/计算、序列化字节、渲染和取消回收成本；测正常例与最坏形态，不只测几十行。
  明确候选预算下哪些样本完整显示、部分显示或不采集，不能用修改成功率代替 diff 可用率。
- 标准库不天然满足硬工作量限制。若采用隔离计算任务，验证实际可终止及资源回收、异常和取消不影响已完成写入；
  不能用取消 await 的方式放任后台线程继续占用 CPU。若库自身有超时/编辑距离上限，仍需验证预算覆盖范围与解析成本。
- 同时核查跨会话 diff 计算的最大并发数、排队数量/总输入字节、等待期限、满载降级以及取消/关闭后的释放。
  原文在等待队列中的内存也计入预算，不能只限制单次 diff；排队或计算不得长期占用文件写锁、数据库事务或事件循环。
  超限只改变 diff 可用性，不把已成功写入判为失败并诱发重写；状态须沿原调用身份关联。
  先核查现有有界执行设施是否满足，满足则复用；不能把会话队列当全局计算锁，也不另造业务执行或调度系统。
- 保留输入合计 256 KiB、私有 diff 对象 64 KiB/1000 展示行作为初始比较基线，不把性能试验变成静默放宽限制。
  大文件小改若频繁降级，提交提高预算或利用确定匹配位置生成有界局部记录的候选，证明准确性与成本后再决定。
- 输出选型记录：采用/淘汰理由、版本与许可证、成本、压力样本实测值、预算建议及仍未满足的边界；
  若没有候选通过，报告阻碍并调整方案，不以“库很成熟”替代验收，也不直接转向手写无限算法。

## 四、D：现有写工具的可信 diff

### 4.1 首版覆盖与工具细化边界

- 保持 `workspace_write` 的模型调用参数及既有结果语义，增加执行层内部的修改证据采集，不要求模型自行生成 diff。
- 覆盖 UTF-8 文件创建、替换和写入相同内容；删除几行属于替换 diff，不等于新增文件删除工具。
  新建空文件即使 `+0/-0` 也必须标为“新建”，相同内容应明确“内容无变化”。
- 每次调用显示“本次修改”，不是相对 Git HEAD 的净变化，也不是整段回答或会话的汇总 diff。
  同一文件多次修改保留各自调用记录，不自动合并、抵消或挪动工具位置。
- D 不新增局部替换；最小局部编辑提前在 G 评审、E 实施并复用 D。仍不新增 `workspace_apply_patch`、
  文件删除/重命名、仓库扫描、文件监听、Git 或 worktree；与 W3 的路径安全和补丁工具设计保持衔接。

### 4.2 采集位置、并发与失败语义

- 在已经授权、解析路径并持有现有写入锁的文件执行层取得本次校验的旧内容及待写新内容；成功写入后才标记修改已应用。
  新建文件旧状态为“不存在”，不能与“原来是空文件”混同。记录前后内容身份，禁止展示时重读当前文件来拼历史 diff。
- 保持现有 expected hash 复核、路径/symlink/敏感文件规则和服务运行限制。授权失败、hash 冲突或写前拒绝不得展示“修改成功”。
- 现有进程内锁不能隔离外部编辑器、Shell 或服务。diff 表达本工具确认提交的内容变化，不保证页面展开时文件仍是该版本，
  也不承诺对外部写入的系统级 compare-and-swap；不能宣称完整捕获所有并发修改。
- 文件写入与数据库不是一个原子事务。写入成功但详情持久化失败时不得回滚文件、自动重试写入或伪造“未修改”。
  取消、进程崩溃与中间失败只记录已观察事实；无法确认提交结果时明确“结果未确认”，不显示可信成功 diff。
- 原生新建过程中可能出现部分写入异常；这类情况不得标为“未发生修改”。首版不借 diff 采集扩大为完整文件事务系统。
- 旧内容、新内容只在本次执行的受控内存中用于计算；不为展示持久化两份完整快照。
  私有采集结果沿执行作用域、防腐层和领域事件交给消息所有者，不能通过模型工具返回正文或公共框架事件旁路传播。
  不允许无界全局字典按路径保存原文；关联到实际调用身份，失败/取消/结束都释放，不能串 execution 或会话。
- 工具结果和 diff 采集结果独立表达。计算超预算或失败不把已成功写入改判为工具失败，也不触发模型重复修改。

### 4.3 预算与表示（建议值，待本计划确认）

- 沿用单文件最多 1 MiB 的写入边界；diff 运算另设预算，不假设 1 MiB 文本的比较一定便宜。
- 单次 diff 的前后输入合计最多 256 KiB、合计最多 10000 行；超过任一值不计算，返回“差异超出采集预算”。
- 序列化私有 diff 对象整体最多 64 KiB（含路径、hunk、行号、标志与转义），最多保留 1000 个展示行，默认上下文各 3 行。
  超长单行不得绕过字节预算；有界前缀展示必须带明确的不完整标记，不截坏 UTF-8 或 JSON。
- 算法必须有可执行的工作量上限；不能只用异步超时包装不可中断的同步计算。高重复行、巨长行等压力测试
  若不能证明有界，须在实施 D 的算法选择关口调整方案，不得先上线无限计算或长期占用事件循环。
- 增删统计只有完整计算后才称“总计”；仅保留部分内容时区分总计与当前展示量，无法完整计算则统计为空而不是 0。
- 结构化行携带增删/上下文类型及前后行号；保留无末尾换行、换行风格变化的提示。控制字符用可见转义呈现，不能静默清除后冒充原始代码。
- 本次 64 KiB 是独立私有详情预算，不改变已有历史分页预算，也不追加“加载完整超大 diff”的隐藏无限接口。
- 256 KiB 输入合计是候选而非已批准体验标准：约 130 KiB 的文件即使只改三行，前后合计也会超限。
  G/D 需用 120 KiB、130 KiB、接近 1 MiB 的代码及高重复行样本评估完整、降级和耗时；E 必须复测大文件小改。
  如日常降级不可接受，先评审提高预算或有界精确局部 hunk 采集，再定稿；不得为通过测试静默放宽运算上限。
  局部 hunk 若采用，须仍能证明是本次匹配、版本校验和成功提交的变化，不接受模型自报 diff。

### 4.4 私有存储、权限与协议

- 优先在既有工具详情密文中兼容增加带格式版本的写入差异表示，与通用 input/output 和 Shell 专用详情兼容。
  保留现有输入/输出能力，但 diff 自身预算独立，不能简单塞进截断的字符串再要求客户端解析。
- 具体字段、可用性、错误及兼容语义在 D 编码前写入工具详情领域协议，并同步内部采集契约和客户端类型。
  本草案不提前把候选字段变为已实现 wire contract；若需要表结构变更，必须先更新数据模型并提供迁移。
- 密文绑定实际 World、消息和调用归属，鉴权后解密；只允许当前 World Owner 及既有会话成员关系读取。
  Guest 不获得路径、代码或私有统计；共享工具 part 仅沿用安全状态/详情能力标记，不加入文件清单或 diff 正文。
- Owner 展开时按需请求；`no-store`，不进入 localStorage、共享历史缓存、机器日志、审计正文、浏览器 trace 或失败报告。
  收起、切换会话/World、退出登录时清除私有正文，并拒绝迟到响应。
- 沿用调用开始后 7 天展示期、启动清理过期密文与消息物理删除级联；回收站不可读。
  工作区解绑或外部文件变更不能把历史差异替换成当前内容；World 备份包含的密文仍按敏感业务数据保管。
- 历史调用未采集时明确“未记录”，不从现有输入、模型回答、当前文件或日志补造旧版本。
  区分等待执行、已记录、内容无变化、预算不足/部分展示、未记录、已过期、不可用与结果未确认。

### 4.5 前端交互

D 在设计私有变更表示和组件边界时考虑“调用 → 文件节点 → 差异块”，避免将整个工具卡写死为一段 patch 文本。
D 首版仍只产生一个 write 文件节点；不提前增加批量调用 schema、批量执行表或工作区扫描。
文件节点身份在 E2 可按父调用与子项稳定关联，第三方 diff 组件只是叶子展示，不拥有工具状态或业务身份。

- 工具卡仍出现在本次调用的实际位置。“实时”指工具完成并保存结果后，已展开的 Owner 卡片自动更新，
  不等整条回答结束；不展示模型尚未执行的内容为已完成修改，不增加逐 token diff 广播。
- 按人工反馈，Owner 写入卡默认展开，进入可视范围后才读取私有详情；仅保留工具卡这一层折叠，
  文件名、操作、`+/-` 统计与 diff 直接显示，不增加文件节点的二次折叠，不展示写入的原始输入/输出。
  后端原始记录与接口为兼容保留，不删除历史数据；E1 编辑展示沿用此方向，不增加新的折叠层级。
- 首版使用统一行内 diff：删除行、增加行、上下文及行号；颜色同时辅以 `+/-`、标签和可访问名称。
  纯文本渲染，不执行 HTML、脚本、终端转义，不自动打开本机路径。首版不提供应用、撤销或回滚按钮。
- 默认限制展示高度并内部纵向滚动；长行软换行但不改变真实行号与源文，避免固定表格宽度下文本溢出着色单元格。
  工具卡折叠和展开保持历史阅读锚点，不抢焦点、不强制滚到会话底部。
- Shell、后台服务和未知工具明确提示“此工具未采集文件差异，不代表没有文件修改”，不能展示空 diff 误导用户。
  不因模型说使用了编辑工具就视为有可信记录；不强制改写 Shell/服务权限或拦截脚本语法。

### 4.6 D 验收与实施关口

1. **契约与采集可行性：** 确认内部私有结果通道、调用身份映射、序列化预算、算法工作量边界和失败语义；
   如果需要修改模型可见工具参数或扩大存储/安全边界，暂停并回到计划确认，不夹带实现。
2. **后端确定性验证：** 创建/空文件/替换/不变、Unicode/换行、hash 冲突、敏感路径/symlink、服务运行拒绝、
   同文件连续与并发调用、异常/取消/崩溃窗口、文件成功但详情失败、计算和展示超限。
3. **权限与恢复：** Owner/Guest、非成员、跨消息/调用/World、密文替换、解密失败、7 天过期、回收站/物理删除；
   重连、重复/乱序事件与刷新后位置及差异一致。验证模型结果、共享 WS、机器日志和失败产物不含新增私有原文。
4. **浏览器：** 真实前后端加 fake Provider，按“前置说明 → 创建 → 中间说明 → 修改 → 最终回答”验证
   执行中/终态更新、二级折叠、行号增删、超限提示、刷新恢复、旧记录降级、阅读锚点与 Guest 拒绝；检查受控占位代码截图。
5. **World 与真实 Provider：** fake managed-world 验证切换隔离；独立 real-world smoke 在本轮隔离工作区内
   通过真实模型执行原生创建、读取、修改并核对 diff。只启用所需文件能力，避免 Shell/服务绕过测试目标。
   授权实施 D 即包含执行这一验收项；执行前说明联网计费，凭据仅进入后端加密边界，关闭 trace/video，不保存原始模型输出到报告。
6. **人工验收：** 用户检查实际位置、创建与修改效果、折叠、刷新、长差异和未覆盖工具提示；明确认可后再提交。

### 4.7 E1 与完整工具组合验收

- 保留 D 的文件能力隔离测试用于证明单项正确性；本节细化 v1.2 已纳入的完整工具集 fake/real-world 场景，
  不新增重复测试项。启用日常文件、结构化命令、Shell 和服务能力，E 实施后包含 edit；
  按 G 定稿的服务策略执行，不能为了得到期望 diff 临时禁用其他入口。
- **至少两轮真实用户交互：** 第一轮要求创建受控页面，经 Owner 审批启动预览并完成回复；
  等待实际 generation 终态后，再以同一服务身份核对托管运行状态和实际 HTTP 页面，确认服务持续存续，
  不能只在工具返回 ready 时检查，也不能用固定等待时长代替 generation 终态和服务就绪事实。
- **第二轮具体局部修改：** 另发一条用户消息，指定修改目标以及必须保留的页面内容；测试不得自行代改文件。
  按模型实际选择的原生工具或脚本路径核验授权、审批和停服策略，原生编辑走停服 → 编辑 → 重新审批启动，
  不擅停其他会话服务；脚本路径依既定执行契约验证，不因缺少原生 diff 自动判为失败。
- **结果独立核对：** 由测试读取本轮受控文件并通过浏览器检查实际服务页面，分别确认目标修改与指定保留内容；
  同时排除旧页面/缓存的假阳性。不能只相信模型回复、工具成功状态、HTTP 200 或 diff 展示。
  文件/页面的受控断言在测试内完成，汇总报告只保留脱敏结果和关联身份，不持久化真实 Prompt 或模型原文。
- fake Provider 确定性覆盖 edit 唯一/无/多处匹配、hash 冲突、片段删除、相同内容、敏感路径、并发及详情失败不重复写入。
- 服务保留任意脚本，验证完整审批、能力说明及覆盖缺口；不把合法脚本写文件误测为必须拒绝。
  共同权限拒绝、批准被移用或篡改由 fake 调用确定性验证，不依赖模型主动产生违规请求。
- 不强制真实模型调用 workspace_edit。**功能与边界验收**和**原生编辑路径观察**分别报告：
  前者记录页面/文件修改、保留内容、审批/停服策略和服务生命周期结果；后者记录实际工具名、
  是否触发 read → edit、哪些调用有可信 diff、哪些未采集或未触发。未触发的能力标为本轮未覆盖，不能借其他路径成功声称通过。
- 不将“所有工具都调用过”作为指标，不为取得期望工具路径无限重跑计费测试。
  正常工作流失败如实报告；路径观察不理想可以回到 G 讨论易用性，但不能刷模型调用直到出现理想结果。
  必要重跑先明确失败原因、范围与有界次数；权限和异常边界继续用既有确定性用例验证，不等待真实模型碰巧触发。
- 检查服务启动返回后仍可能写文件的提示；Shell、服务及以后扩展的结构化命令不因名称或结构化参数被视为无副作用。
  当前固定 pwd/list/read/count 的事实不扩展成未来所有结构化命令的安全承诺。
- 服务运行中原生编辑按 G 定稿策略明确拒绝并提供可继续流程，或经独立批准后验证允许策略；覆盖其他会话占用、
  清理待确认、停服失败、重新启动需新审批，不能依赖杀掉全部测试进程规避竞争。
- 完整工具集 real-world 与单项 smoke 均为独立计费验收，执行前告知；使用受控文件与测试服务，
  不请求访问真实用户项目，不额外持久化私有内容。E 与工具组合人工验收完成后才宣称编辑体验阶段完成。
- **过程存续与最终回收分开：** 第一轮结束不清理仍需第二轮使用的服务；停服编辑时验证正常回收和新审批启动，
  用例最终结束再通过产品正常停止/回收路径清理本轮登记资源。成功、失败、取消均进入本轮清理收尾，
  不清理正式环境或其他用例/会话的资源。
- 正常回收失败独立记录并保留该失败结论；测试框架因安全兜底而紧急回收时，单独记录目标身份、原因和实际结果，
  不能把“紧急清理成功”改写为“产品正常回收通过”。无法确认回收时明确报告残留/未知状态，不仅凭根 PID 消失断言清理完成。

测试工作区按类别/时间戳/用例分层，使用独立数据库，遵守既有保留与清理规则，结束后回收启动的服务。
如涉及 schema，必须完成 SQLite 迁移重放及 PostgreSQL 方言离线编译；离线编译不能描述成 PostgreSQL 实例验证。

## 五、E2：批量文件操作与调用归组（探索归组已人工验收，批量执行未实施）

### 5.1 两类能力分别交付

- **真实批量调用：** 模型一次请求读取多个文件，或创建/替换/局部修改多个文件；服务端逐文件执行并返回独立结果。
- **展示归组：** 将时间线上适合归组的相邻 Read/List/Search 调用放入可折叠探索记录；底层仍可以是多次调用。
  不能因界面归组就声称后端一次调用、并行执行或整批事务。
- 复用 E1 已完成的单文件原语、D 的私有记录和文件节点，不引入新业务 execution/调度系统。
  批量入口采用兼容新增工具还是扩展已有参数，在 E2 编码前定稿；单文件调用保持可用，前后端真实工具标识一致。
- 第一版批量操作只针对当前会话绑定的同一 managed_directory 工作区，不跨 World/工作区，也不开放群聊 Agent 执行能力。

### 5.2 批量执行与失败边界

- 每个子项有父调用身份、稳定子项标识、目标文件、操作类型及独立状态。默认按请求顺序显示，不能按完成顺序打乱节点。
  复用已有 Trace 与实际工具调用身份，不为展示额外造一次 Agent execution 或虚构工具调用。
- 每个文件分别经过权限、containment、symlink、敏感路径、文件大小和 hash 校验；本轮停服原生编辑规则不变。
  参数与目标预检失败时不开始写入；执行期间仍逐项复核，预检不是外部写入隔离或跨文件原子事务。
- 首版同一批次同一规范目标最多一个写子项，重复/别名冲突目标明确拒绝，避免多个 expected hash 相互失效。
  跨批次仍受既有写入冲突规则约束，不因批量模式绕过版本校验。
- 批量读取采用有界并发，每项独立返回错误；读取多文件不承诺同一时刻的快照，各自保留来源版本/hash。
  写入首版顺序执行，遇到首个执行失败停止启动后续项，明确列出已成功、失败和未执行项，不自动回滚先前成功文件。
- 取消时不再启动后续项，等待当前项在受控边界收尾；无法确认落地结果标为未确认，不能猜测未修改。
  父级结果表达完整成功、部分完成、失败/取消或结果未知，不把部分成功简化为整批成功。
- 重试只针对已明确失败/未执行项，使用新的有效版本证据；已成功子项不再次执行，结果未知项先核查，不能整批盲目重放。
  同一请求的重放/幂等语义及崩溃恢复标记须在 E2 协议定稿，不默认框架自动重试安全。
- 同时设置整批文件数、输入/输出字节、在途原文内存、并发和排队上限；每文件仍有上限，但不能简单累加成无界总量。
  read 结果的片段、全文件 hash 和错误字段必须保持可用，不通过粗暴截断 JSON 丢掉版本证据。
  具体数值按 E2 规模测试确认，不在本次纳入计划时默认提高 D/E1 预算。

### 5.3 文件节点与探索归组

用户已确认展示归组定义，本次先实现可独立验证的探索归组切片，再进入批量 schema 与执行：
连续两项及以上原生 Read/List 显示默认展开的“探索”容器；单项保留原工具卡，后续追加不重挂载已显示工具。
摘要按读取/列目录的调用次数计数，不把重复读取当作不同文件；仅在各项明确成功时显示已完成，折叠仍显示失败、
拒绝、取消、中断和未知状态。用户折叠后，流式追加或调用完成不得自动展开/折叠；刷新重新默认展开，不持久化私有详情。
只处理 timeline_version=1 的角色消息；缺失/重复身份、旧版或未知版本不猜测。文件名不为摘要自动预取，
仍经 Owner 主动展开的既有详情入口查看。隐藏子项的阅读锚点回退到组标题，避免使用隐藏 DOM 的零矩形校正滚动。
本切片不改变服务端权限、消息字段、执行或数据库，不宣称 E2 的批量子项、重试和预算已完成。

- 一个批量工具卡展开为多个文件节点，每个节点可独立查看状态、错误、读取结果或折叠 diff；部分失败不隐藏已成功结果。
  总增删数只有完整统计可得时才称总计；超限/未采集节点不当作零变化，不能将修改次数总和称为文件净变化。
- 文件路径、源文、搜索参数及 diff 沿用 Owner 私有详情边界；Guest 只看已允许的共享摘要。
  共享消息/WS 不携带私有文件清单，不为批量模式取消加密、期限、资源鉴权或按需加载。
- 探索归组只覆盖相邻、具有可靠结构化类型的只读调用；保留每次调用的真实名称、身份、状态、耗时与展开入口。
  不跨 AI 正文、写操作、审批边界或不同 execution 归并，也不按脚本字符串猜测 Shell 是 Read/Search。
- 刷新、断线恢复、流式更新和展开后保持真实顺序与阅读锚点；不将工具重新移动到回复末尾。
  旧记录仅按已有事实展示，不补造批量父子关系或将部分记录伪装成完整历史。
- 原生 Search 仍按 W2b 计划实施；E2 先支持现有 Read/List 的归组方式，不为了仿照截图提前新增搜索工具。
  W3 的 worktree 补丁、文件删除/重命名等能力不被批量 managed_directory 写入替代。
