## 后续执行顺序建议

建议先补齐现有聊天和工作区的使用闭环，再按目标推进仓库协作或编排；导出/导入、上下文容量等独立需求可以提前安排。以下是重排后的建议，不表示本次已经启动实现；同一层中的工作按需求选择，无须全部做完才进入下一层。

| 建议顺序 | 工作 | 相比旧排期的调整 |
|---|---|---|
| 1 | 现有流程维护，以及工作区绑定/切换的界面完善 | 修复、体验和测试环境问题随需求处理，不等待 W2a、Orchestrator 或新的总预算系统。聊天标题工作区入口可从旧 W2a 单独拆出。 |
| 2 | 独立产品闭环：会话导出/导入、群聊工作区授权，或明确需要的 Guest 邀请/MCP 接入 | 每项独立定范围；群聊工作区不必和 Repository 表一起交付，导出不再等待编排、Checkpoint 和缓存基准全部完成。 |
| 3 | 按目标分支推进：Repository/Git 只读能力，或最小文本 Orchestrator | 仓库与编排可以分别安排。文本分派复用已有 execution/串行调度基础，不要求先有 Git/worktree。 |
| 4 | 并行代码协作 | 在资源绑定、授权复核和写入隔离方案具备后，再开放并行修改；若选择 Git worktree 方案，则先完成 Repository/Git 与 worktree 生命周期。 |
| 按实际瓶颈插入 | Checkpoint、缓存优化、运行中原生编辑、长期记忆与其他能力库 | Checkpoint 可在长会话容量成为问题时提前；Memory 不作为聊天/导出的前置。运行中编辑单独处理并发与服务生命周期，不与搜索/批量修改绑定。 |

## 保留的实际依赖

| 要做的能力 | 需要解决的前置问题 | 可以解除的旧绑定 |
|---|---|---|
| 会话导出/导入 | 明确当前支持的数据范围、格式版本、资源重建和敏感数据边界 | 不依赖未实现的编排或长期记忆；未来字段可通过格式兼容演进。 |
| 群聊使用工作区工具 | 群聊资源绑定、触发者/角色授权、租用归属、停止与成员撤销测试 | 不要求先引入 Git 仓库；不能只放开前端开关。 |
| 文本 Orchestrator | 参与角色授权、父子 execution、有限并行、取消、失败汇总和消息所有权 | 不依赖 worktree；已有 E0 不必重做。 |
| Git/worktree | Owner 授权的 Repository、路径/版本校验、工作区创建/回收与冲突处理 | 不依赖导出、MCP、Memory；原生搜索已经实现，可直接复用。 |
| 并行文件修改 | 明确写入隔离、版本冲突、结果交接与取消恢复 | 不能仅靠会话队列或多 worker；worktree 是可选设计方案，选用后才形成相应依赖。 |
| Checkpoint/Memory | 上下文边界、来源/版本、失效与权限隔离，失败回退 | 不要求先完成全部代码协作能力；二者也不必绑定交付。 |

具体任务采用其中一项时，再补齐该项设计与验收；无需为调整普通任务顺序重审全部历史计划。现有 Owner/Guest、Shell 审批、凭据和未知副作用处理边界继续适用。

新计划应明确状态、目标、采用范围、待解决取舍与验收方式。已完成内容的当前字段/限制只在领域协议维护，阶段摘要引用协议和验证记录；旧验收和提交方式不自动约束维护任务。具体工作规则见 [AGENTS.md](../../AGENTS.md)。
