## 一、问题与目标

当前 Agent 的服务状态/日志/停止工具均需提供 runtime_id；Owner `/ps` 已有列表能力，但模型没有发现入口。
服务可以跨 generation 存续，不能要求模型始终记得历史 ID，也不能把上下文摘要或记忆当成资源事实来源。

当前 write/edit 的说明已经提示停服规则，但授权帮助函数以 None 合并多类拒绝，最终常返回
WORKSPACE_TOOL_NOT_AVAILABLE。模型知道可能的原因，却无法确认本次是否真正被服务占用。
限制范围实际是整个工作区，不仅当前会话；其他会话的服务也可能阻止原生修改。

本计划先完成两个目标：让 Agent 找回本会话登记服务，并获得可操作、真实且不越权的拒绝原因。
随后单独评审运行中编辑；不得为改善提示而直接删除现有检查，也不将提示词当作权限隔离。

## 二、阶段与验收关口

| 阶段 | 交付 | 明确不做 |
|---|---|---|
| S0 契约定稿 | 查询授权、分页、拒绝分类与隐私字段，更新领域协议及测试矩阵 | 不把候选字段写成已实现接口 |
| S1 服务发现 | 扩展现有状态工具，支持不提供 ID 的列表查询 | 不新增重复工具，不扫描全机，不自动停止 |
| S2 拒绝诊断 | write/edit 单文件与 items 共用准确拒绝原因及下一步提示 | 不放开运行中编辑，不绕过审批 |
| 人工验收 | S1/S2 作为一个完整排障切片，自动验证后人工确认、独立提交 | 不因前阶段验收自动批准 S3 |
| S3 运行中编辑评审 | 状态矩阵、并发与用户控制方案，另行确认是否实施 | 本计划不直接授权取消运行中写入限制 |

## 三、S1：扩展现有服务状态工具

### 3.1 入口与范围

S1 实施定稿：workspace_service_status() 或 cursor/limit 为列表形式，limit 默认 50、最大 100；
runtime_id 形式与 cursor/limit 键互斥（含 null/默认值），显式 null/空 ID 拒绝，列表 cursor=null 表示首页。
列表仅列本会话非终态 service；指定 ID 保留原已登记实例查询兼容（包括终态，原可查询的 command 也不收窄）。
列表返回 items/has_more/next_cursor，每项仅 runtime_id/state/port/health_code/workspace_binding_id；
本切片不返回 can_stop，避免将不完整能力判断当作停止授权。单项查询仍为原四字段响应。
游标沿用项目不透明位置游标思路，绑定当前 epoch、Owner、会话及 sequence/id，重启或换 World 后重新查询；
游标不授予权限。查询只投影必要列，不加载加密日志；输出 JSON 上限 64 KiB，失败不截断或返回伪空列表。
用户先授权实现 S1，随后单独验收并批准提交；S2 另行实施与验收，不因 S1 通过而视为完成。

拟兼容扩展 workspace_service_status：

- 提供 runtime_id：保持现有指定实例查询及响应兼容。
- 不提供 runtime_id：列出当前调用所属会话的托管常驻服务；不是列出所有 OS 进程或一次性命令。
- 列表和指定查询参数互斥，null/空 ID、未知字段的含义在 S0 明确，不依赖模型自行解释。
- 作用域从宿主 execution/会话身份取得，不接受模型指定其他会话、World、Owner 或工作区。
- 复用 `/ps` 的登记数据、归属及状态定义，但不直接把包含历史详情的完整 REST 响应交给模型。

默认包含尚未终结或仍需核查的登记实例：待审批、启动/等待就绪、正常运行、不健康、停止中、清理待确认。
这些状态必须保持差异，不能一律称为“运行中”。首版不新增终态历史列表；已知 ID 仍可查询其已保存终态。

候选安全字段为 runtime_id、真实 state、port、已记录的健康结果、工作区引用和可用操作提示。
不返回完整脚本、环境变量、绝对目录、日志正文、凭据或其他会话聊天内容。
可停止提示只是查询时的判断，不是停止授权；执行停止时继续复核权限、资源归属和状态。

### 3.2 有界分页与状态变化

配额可调，不能依赖“默认每会话三个”来保证结果始终很小。拟默认每页 50、最大 100 项，完整 JSON 最大 64 KiB；
实际数值在 S0/规模测试确认。返回完整结构化节点与续页信息，禁止粗暴截断 JSON 或静默漏掉剩余实例。
使用既有稳定登记顺序与作用域绑定游标，不新造服务身份；持续变化的列表不是同一时刻快照。
跨页可能遇到实例退出或新实例出现，必要时重新查询；停止/修改前重新判断，不将旧列表当永久事实。
数据库、解密或查询失败不得伪装成空列表；无结果才明确返回空列表。

### 3.3 查询授权与执行授权分开

保留 Owner、当前有效 single execution、活跃角色、角色显式启用状态工具、会话成员关系和资源归属检查。
Guest、其他会话实例、已删除会话或已撤销角色权限不得因为知道 ID 而获得信息；不可见资源按既有隐藏规则响应。

只读发现不应要求先拿到可写文件租用，也不应被启动开关关闭、服务名额用尽、Shell 平台不可用或清理门槛直接阻断。
特别检查工具创建阶段，而不只改工具函数内部：原工厂不能在查询前就把状态工具排除。
应允许读取本会话既有服务登记，即便其历史工作区与当前绑定不同；不因此开放历史工作区文件访问。
复用现有身份校验与查询服务，按操作目的区分策略，不复制另一套 Owner/成员权限实现。
日志读取、停止和启动不随列表查询自动放权，保持各自既有权限和逐次复核。

以上只保证应用仍可服务且当前 execution 有效时的排障查询；应用已关闭、执行已取消、身份已撤销时不承诺继续调用。

## 四、S2：准确的拒绝原因与可继续的流程

### 4.1 原因分类

S2 实施定稿：保留现行可执行条件，仅将内部可用性判断类型化。身份/成员/执行失效或目标非本 Owner 所有时仍为
WORKSPACE_TOOL_NOT_AVAILABLE，无诊断对象；已通过这些边界后区分能力变化、绑定变化、租用不可用、目录不可用。
有效绑定上的运行时阻塞按“未确认回收/失败清理 → World 关闭 → 进行中的范围清理 → 单项停止中 → 其他未结束服务”优先级判断。
本切片不修改 Shell/状态查询/停止的执行策略，也不取消停服限制。

模型与 Owner 详情中的可选 diagnostic 格式为 version=1、reason、scope、executed=false、message、next_steps、
recommended_tool（仅实际暴露且仍获准的 workspace_service_status 或 null）、services（最多3个本会话 ID/state 或 null）、
services_truncated、other_sessions_blocking（未查询时 null）。完整紧凑 JSON <=2 KiB，建议不含自动停止或绕过脚本。
无状态查询权限时不返回实例明细，提示 Owner 使用 /ps；其他会话或历史归属服务仅汇总有无，不返回 ID/标题/脚本。
单项 write/edit 结果兼容增加 diagnostic；批次仅失败项携带，不能把 executed=false 解释为整批没有写入。
复用原加密写入详情，不增加表或第二份审计；共享工具卡/WS/正式日志仅传固定错误码，完整诊断由 Owner 按需读取。

先完成身份与资源归属校验，再返回有权知道的业务阻塞原因。身份/归属失败继续使用不泄露资源存在性的响应，
不能给未授权调用者附带服务数量、ID 或工作区细节。

对于已授权的文件操作，至少区分：

| 实际原因 | 应告知模型的事实与下一步 |
|---|---|
| 工作区存在尚未结束服务 | 原生修改因现行服务占用策略被拒绝；查询并协调停服后重试 |
| 服务正在停止/回收 | 停止动作尚未完成；查询真实状态，不按固定睡眠时长假定已结束 |
| 清理待确认 | 缺少完整回收证明；Owner 核查/重试既有回收流程，不能凭 PID 消失直接放行 |
| 工作区/World 正在关闭或有阻塞清理操作 | 当前生命周期门槛不允许写入；完成相应操作后再重新判断 |
| 工具开关、角色权限或绑定已变化 | 本次调用不再满足能力条件；按可披露范围提示检查配置，不误报成服务占用 |

具体错误码、分类优先级、错误终态和可重试条件在 S0 写入错误码注册表；以上是语义需求，不是现行可用码。
多种原因并存时优先提示需要人工核查的回收问题，不能只列出一个正常运行实例就让 Agent 误以为停它即可解决全部阻塞。

### 4.2 有界诊断与可见性

建议结果包含固定原因、作用域、是否已执行、当前会话相关实例摘要及下一步建议；字段在 S0 定稿。
诊断明确区分“工作区被阻塞”和“阻塞者归属本会话”。

- 本会话实例可在有状态查询权限时获得 ID/状态；未启用该工具时提示 Owner 通过 `/ps` 查询，不借错误响应绕过查询权限。
- 其他会话的阻塞实例只返回经过允许的汇总，例如“同工作区存在其他会话服务，需 Owner 协调”；
  不泄漏对方 runtime_id、脚本、会话标题或日志，不授权本会话停止它们。
- 阻塞清单过长时返回有界摘要和查询指引，不超限持久化全部资源。
- 建议中的可用工具必须来自本次实际工具集；不能推荐未暴露工具，更不能建议改用 Shell 绕过拒绝。
- 指定 ID 可能已经终结或不存在；依赖真实查询结果，而不是从模型记忆/异常文本推测资源状态。

模型可见的诊断、Owner 私有详情和共享工具卡分层处理：共享消息/WS/正式日志只传既有允许的安全摘要及固定错误码，
不因改善提示把完整实例清单或其他私有信息广播给 Guest。需要展开的详情复用原加密通道、保留期和身份绑定。

### 4.3 单文件与批次一致

统一文件授权帮助函数须返回明确的内部判定，而非用一个 None 混同所有原因；不向调用者暴露底层异常对象。
write/edit 的 path 与 items 形式共用判定与提示，旧客户端对新增安全字段能降级，具体兼容性写入领域协议。
批次预检失败仍无写入；逐项执行时新出现阻塞则停止后续项，保留已成功项及其 diff。
提示只能针对失败项说明“本项未执行”，不能在部分提交后写成“本批没有修改任何文件”。
服务状态、配置或权限在查询后改变时仍以执行前复核为准；更详细的诊断不是预先授权或写入隔离。

## 五、S3：运行中编辑另行评审

倾向评估允许正常开发预览服务存续时进行原生编辑，但不预设所有 ready/unhealthy 状态都应该放行。
服务本身和获批脚本仍能修改文件，现行停服规则不是安全沙箱；取消该规则也不意味着获得并发一致性。

评审必须覆盖：

1. 启动准备、等待就绪、正常服务、不健康、停止中、清理待确认和 World/工作区关闭各状态的可写矩阵。
2. 单文件原子替换与新建过程、多个文件非原子提交、服务读到半批项目、watcher/HMR/构建重启的实际表现。
3. 服务或外部编辑器同时写入时的 hash 冲突，以及现有锁无法覆盖的进程级写入；不承诺自动协调或回滚。
4. 是否需要 Owner 显式工作区开发策略及默认值，如何告知“文件已修改但服务未正确重载”，而非把文件成功等同页面成功。
5. 其他会话服务共享工作区时，如何协调修改影响；不得自动停止他人服务，不提前实现临时群聊协商。
6. 独立验证文件内容与实际页面、批次中途失败、停止/回收竞争及后端退出；保护必要的关闭与未确认回收门槛。

S3 的输出先是一份经确认的策略修订及验收标准，再决定编码。不实现完整跨平台沙箱、服务自动重启或工作区事务。

## 六、验证要求

确定性后端测试覆盖：列表/指定查询兼容、空列表、所有非终态、超默认配额后的分页与字节预算、并发状态变化、
角色/Owner/成员撤销、跨会话与跨 World、启动开关关闭或满额时仍可查询、查询不占配额且不产生文件/进程副作用。
查询失败不能返回空列表；失效 ID、终态 ID、不可见 ID 必须各自符合契约。

拒绝诊断覆盖单文件与批次、不同阻塞类型及并存优先级；特别覆盖其他会话占用、状态查询未启用、
预检后服务状态/权限变化、已有成功项后被阻塞、清理待确认和关闭门槛。边界不用真实模型碰运气触发。
使用 fake Provider 构造“当前上下文没有原 runtime_id”的场景，验证通过查询找回，而非测试偷偷把 ID 塞入提示词。

Playwright 启动真实前后端，验证 Owner 查询/拒绝详情、正确下一步、Guest 无私有实例清单请求、刷新恢复；
至少包含成功路径与关键权限/拒绝路径。保留受控截图，按类别/本轮时间戳/用例分层组织测试数据。

真实验证复用既有完整工具集两轮开发场景：首轮启动服务并结束回复、确认服务继续存续；第二轮允许查询当前服务后
修改受控文件，独立核验文件/页面与正常回收。不得假装模型忘记了仍在上下文中的 ID，也不强制特定工具路径；
真实报告分别记录列表调用是否发生、拒绝提示是否触发、最终功能与回收结果，未触发的能力由确定性测试证明。
使用独立命令、数据库和受控工作区，运行前说明联网与费用；不为取得期望路径无限重跑。成功、失败、取消均清理本轮资源，
紧急兜底不能掩盖正常回收失败，绝不清理正式用户服务。

S1/S2 预期不新增表或第二套调度/Trace；若实现发现确需 schema 变化，先修订计划并补迁移、SQLite 重放与 PostgreSQL
验证要求，不能以运行时建表绕过。未完成的真实验证或平台覆盖如实报告。

## 七、实施时的文档更新与退出条件

本计划是范围/验收权威；S0 定稿时更新服务领域协议、工作区工具契约、错误码注册表、Agent 内部契约、客户端类型与测试。
私有诊断如扩展存储格式，同步工具详情及数据模型文档；只改格式不虚构新增表。协议入口和 README 只更新状态与链接。

退出条件：S1/S2 行为与权限测试通过、真实场景按实际覆盖报告、测试资源正常回收，交用户人工验证后独立提交。
人工验证重点为“忘记 ID 仍能查到”“拒绝原因明确且能继续处理”“不会擅停其他会话服务”。
本次编写计划不视为批准 S3 实现，也不改变 E2 已验收的停服编辑策略。
