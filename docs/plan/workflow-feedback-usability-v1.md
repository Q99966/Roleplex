## 1. 问题与现有基础

| 已观察问题 | 改进目标 |
|---|---|
| 主流程、并行分支、条件与返工回线混在同一视图，长线重合；任务/判断/汇合外形接近，编号容易被误认为执行顺序 | 先读懂阶段主干，再展开具体任务；条件和循环含义可直接辨认。 |
| 审查报告用同一个 `approved=false` 表达实现缺陷、契约冲突和缺少运行验证能力 | 准确分类并交给适当责任角色，避免所有问题都进入开发返工循环。 |
| 角色正文希望向协调者/架构师反馈，但文本中的 @ 不等于实际派发 | 反馈有明确来源、处理者、处置记录和复核结果，能关联到真实任务或图变更。 |
| 模板/本次运行、全局/节点、规划/启动/重规划、本地/服务端保存和历史记录散落在多处 | 在当前上下文中提供少而明确的操作，持续显示作用对象与生效范围。 |

已具备的读图、整图写入、按 ID 局部编辑、图版本、运行检查、停止/重试、并行循环与资源准入继续复用。人工和协调者已经能修改图；本阶段补齐的是问题级反馈处置和用户可理解的操作链，不重新开发另一套图服务。

原基线的 `workflow_result` 仅支持结构化标量结果与摘要。第一批已在此基础上增加反馈登记、转办、处理与关闭，旧图管理验收只证明其原覆盖范围；新增能力以本批验收为证据。

本轮聚焦群内协作。世界 Orchestrator、桌宠 API、跨群委派、Git/worktree、新的预算系统及普通群聊工具权限扩张不作为前置。

## 2. 第一批：反馈与局部处置

### 2.1 分开记录执行结果、业务结论与反馈

每个结束的节点尝试都应能定位到原消息、结果与执行事实；有问题时再登记需要处置的反馈。正常成功不强制生成额外模型总结或创建无价值的问题记录。

“模型执行结束”“业务检查通过”“反馈已经解决”是三件事。保留原 execution/message 终态，业务结论和待处理反馈单独展示；未运行的验证保持未验证，未知文件结果保持未知，不自动转换成成功或失败。

| 反馈类型（产品语义，非最终 wire 枚举） | 处置方向 |
|---|---|
| 实现缺陷 | 定位相关文件、节点和证据，交给有权限的开发角色修复，再复核受影响结果。 |
| 需求/契约冲突 | 由承担该职责的架构角色或 Owner 裁决，更新权威说明并记录理由，随后按新版本复核；不能为拿到“通过”而擅自降低验收要求。 |
| 能力缺口 | 后台对照本节点实际分配核验，安排具备授权能力的验证节点，或等待 Owner 配置/人工验证；不只采信模型自述，也不自动开放新权限。 |
| 未验证/证据不足/结果未知 | 核查已有事实或追加验证，明确缺口；不因有正文报告就宣称已经做过运行验收。 |
| 改进建议 | 说明收益和影响，按需求决定是否采纳；建议不自动成为阻塞全部后续步骤的规则。 |

允许一份节点报告提出多个问题，各问题分别归类和处理。`approved` 可继续作为既有节点的业务字段，但不能成为平台对全部反馈的唯一分类；旧图不会在升级后被偷偷改写条件。

### 2.2 反馈来源与生命周期

- 反馈关联当前群、run、图版本、node、activation、attempt、循环轮次和结果版本；实际提交者身份由后台绑定，模型不能伪造来源。Owner 从节点、结果或原消息发起反馈时自动带入同样的来源引用。
- 内容包含问题说明、类别、影响范围、证据引用和建议处理角色。模型建议只作为数据，不能通过“请 @某人”文本自行取得派发权或改变其他群任务。
- 原反馈与后续处置分开保留；图变化或新尝试不会抹掉旧意见。来源失效、结果已被新版本替代时明确标注，不将旧反馈应用到无关的新节点。
- 处理过程至少可辨认“待处理、处理中、等待裁决/补充条件、待复核、已解决”，以及有理由的“未采纳、接受遗留或不再适用”。接受遗留不冒充修复完成。
- 提交、重复通知、处理、派发和图修改都有幂等与版本边界。新模型回复没有实际证据或处理记录时，不能仅凭“已解决”关闭问题。
- 优先扩展现有结果交接与业务存储，反馈记录引用原消息/工具事实，不复制完整输出、源码或另一套 Trace。新增 schema 提供迁移并更新数据模型；反馈正文和证据敏感内容不进入正式日志。

### 2.3 何时交给协调者

普通结果按既定依赖交接；需要裁决、缺能力、关键失败或影响后续目标的反馈才触发协调处置。相关并行节点的意见可以合并处理，不要求每个成功节点都额外调用一次协调者模型。

协调执行在 Owner 本次已声明的运行管理范围内，可以据反馈创建新的有效协调执行，复用预算和父子关联；不复用已经结束/撤销的临时授权。已授权的正常调整无需逐条重复人工确认；没有对应管理授权时登记为待处理，并提供 Owner 显式交给协调者的入口。

同一反馈或关联问题不会因重连、重试或多个节点同时完成而重复唤醒；并发处置同一范围需有版本协调和取消语义。协调者更换/撤权后，旧执行不能继续消费意见、派发或改图。

阻塞性反馈只使受影响的依赖路径等待，无关并行任务可以继续收口。等待原因应可见，不能伪装成 Provider 异常或把全部反馈都当作重试指令。人工授权、任命与工具审批仍由 Owner 完成。

### 2.4 从反馈到局部修正

处理链为：**查看来源与事实 → 分类并确定处理角色 → 选择处置 → 应用授权修改或派发任务 → 复核 → 记录结果**。

- 不同问题可通过补充任务说明、创建新尝试、增加裁决/验证节点、调整尚未派发子图或未来循环轮次处理；不要求每条反馈都修改图，也不重建整张图来处理局部问题。
- 复用 `workflow_inspect_run`、`workflow_read_graph`、`workflow_edit_graph` 及现有控制入口。后端记录反馈、协调执行、图修订和后续尝试之间的关联，人工与模型操作使用同一服务。
- 修改前后能查看目标是模板还是本次运行、具体变更和受影响路径。已经授权自动处理的变更可直接提交并保留可查看记录；需要 Owner 决定的情况先展示建议与影响。
- 已完成节点保留历史；需要再次处理时创建新节点或新尝试。运行中的输入/权限保持冻结，未确认副作用先核查，循环修改在已有安全边界采用；不借反馈绕过保护节点或版本校验。
- 多条反馈引起的相关变更可按原子批次提交；变更冲突或提交失败时反馈仍保留可处理状态，不显示虚假的“已采用”。
- 处置完成还需复核受影响结果；仅修改图、仅派发任务或仅输出一段说明不算问题已解决。仍有未验证/遗留事项时，交付汇总明确列出，与全部通过区别展示。

### 2.5 人与协调者的最低操作覆盖

| 操作 | Owner 界面 | 群 Orchestrator |
|---|---|---|
| 查看节点结果、来源、版本与反馈 | 能定位原消息/尝试和证据 | 在授权范围内获得相同事实引用，不依赖猜测聊天末尾 |
| 提交反馈、补充证据或说明 | 从选中节点/消息直接提交，不要求复制整份报告 | 工作角色通过受控结果/反馈接口报告，只绑定自己的真实执行 |
| 分类、确定处理角色和处理状态 | 可直接处理或交给协调者 | 按职责与授权提出/执行处置，解释依据 |
| 查看修改及影响、局部改图 | 能编辑并查看精确差异，作用对象明确 | 通过既有图工具操作同一对象，返回实际提交结果 |
| 重试或继续受影响步骤 | 精确选中尝试与依赖范围 | 经事实核对和授权执行，不重放未知副作用或刷新预算 |
| 复核、未采纳或接受遗留 | 有明确原因及记录 | 在被授予的职责内处理；不能代签 Owner 人工确认或自行豁免受保护要求 |

双方共享业务能力与校验，不要求获得相同的管理权限。更改任命、扩大角色权限、人工确认和 Shell 审批等继续维持已有 Owner 边界。

## 3. 第二批：图的可读性

本批已实现，验证见[可读性记录](../testing/workflow-readability.md)。包含阶段/循环投影、拓扑与循环区域布局、坐标保留和撤销、分支文案、关系图层、节点/反馈聚焦、窄屏定位及展示元数据兼容保存。恢复副本前确认旧编辑已落盘；纯展示修订保留正在规划/汇总的阶段、分工和原执行记录。没有引入新布局库或新的执行节点类型。

保持现有浅蓝/薄荷工作台风格，以“阶段总览 → 节点细节”为主要组织方式。此批首先改变展示，不改变执行语义。

- 默认总览突出主干，例如“架构设计 → 并行实现 → 集成 → 审查与修订 → 交付”；阶段或循环可以折叠，展开才显示内部任务。折叠摘要仍显示关键等待、失败和未处理反馈，不能隐藏异常。
- 布局由前端根据拓扑和显式循环计算：主干方向一致，并行分支分层对齐，汇合位置明确，回边沿循环区域外侧独立走线。不能只做连线避障后依赖模型手写坐标决定整体布局。
- 任务、判断、汇合、人工确认使用可辨认的形状/图标；角色身份用名称/标签，运行状态用一致的语义颜色与文字。保留已有自定义颜色，不能把条件类型的颜色冒充错误状态。
- 分支优先显示有业务含义的标签，如“通过”“需要修订”“等待裁决”；标签可配置并能查看实际条件。未声明含义时使用“条件成立/不成立”，不把任意 true/false 都翻译成通过/失败。
- 显示循环名称、范围、当前轮次与出口；创建序号只用于定位，不冒充实际执行顺序。图的控制依赖、结果输入和反馈关联可区分，避免用同一种实线混画所有关系。
- 选中节点或反馈时突出相关上游、下游及处理路径，其余关系弱化。提供适配视图、聚焦选中、一键整理等明确操作；不强迫把全部节点缩小到文字难以阅读的程度。
- 新生成草稿可以采用自动整理；已有手动位置默认保留，用户主动整理才调整全图。模型增量新增节点时优先局部安置，拖动/整理只改变展示字段，不重接业务连线或清空草稿。
- 阶段分组和折叠是展示投影，不能为减少节点数量删除执行任务。需要持久化的标签/分组等展示元数据保持兼容，不复用业务 loop 声明伪造只是视觉上的区域。

图仍使用现有 React Flow 和图编辑服务。本计划不指定新的画布库；布局实现与依赖选择按现有技术栈处理，不另设阻塞业务的选型阶段。

## 4. 第三批：操作面板整理

收敛为**一条主工具栏、一个画布、一个上下文面板**。保留现有覆盖主聊天区的方式，不另开产品页面；原应用侧栏与群成员管理职责不变。

| 区域 | 内容与行为 |
|---|---|
| 顶部工具栏 | 流程名称/选择、明确的“模板/本次运行/历史只读”对象、保存或运行状态、当前主要操作及更多菜单。运行方式可选择，但不平铺多个含义接近的启动按钮。 |
| 中央画布 | 阶段总览、节点、连线、反馈标记与视图控制；不塞入所有配置表单。 |
| 右侧唯一上下文面板 | 未选择对象时看流程概况；选节点时看任务/结果/反馈；选连线时看跳转条件；选反馈时看来源、处置和关联变更。避免工作流侧栏和画布内部再同时出现两个属性区。 |
| 按需打开的记录/高级设置 | 图版本、修改记录、协调请求、完整执行记录、并发配置、详细循环声明、兼容说明与草稿恢复副本，不与日常操作同层堆叠。 |

- 操作名称表达作用对象和效果：例如“保存模板”“提交本次运行调整”“继续剩余步骤”。保存、启动、人工确认与运行重规划保持语义区分，但按当前状态提供相关操作。
- 选中节点可直接反馈、查看其处理进展或请求局部调整；处理入口不用用户先去历史对话找文本，再复制到另一个全局输入框。
- “执行内核 v1/v2”、原始字段名与 JSON 等实现细节放入兼容/高级查看；正常使用以并行、条件、循环等业务概念表达。旧图真实支持边界仍准确说明，不静默改变执行模式。
- 本地草稿与服务端提交状态合并为简洁状态提示；恢复/导出等在需要时出现。保留现有或同期完成的本地恢复、未保存编辑、冲突处理与身份隔离能力，不重造另一套草稿存储。
- 运行有效图、待采用修订和历史图明确区分；选择历史只改变查看对象，不触发执行，不把历史修改提交到错误目标。
- 小屏保留主要动作，详情和记录按需切换；键盘可完成选中、查看、反馈和操作。使用稳定可访问名称、明确焦点、非颜色提示和减少动画偏好。

## 6. 分批验收与退出条件

每批都包含自身必要的功能与回归验证，不把测试全部推迟到最后。历史图管理通过记录不能替代本阶段的反馈或视觉验收。

| 批次 | 成功路径 | 关键失败/边界 | 完成证据 |
|---|---|---|---|
| 第一批：反馈与局部处置 | 审查提出契约冲突，协调者登记/分类并安排架构裁决；局部调整后续任务，只执行需要处理的部分，复核后反馈有准确终态 | 重复/乱序通知、并发处置冲突、撤权/停止、来源过期、能力不足、未验证结果、改图失败；无关分支不被误停，文件不被盲重放 | 确定性后端/并发测试、真实前后端 fake 浏览器成功与拒绝路径，以及独立真实 Provider 协作验证 |
| 第二批：图可读性 | 受控示例含并行、汇合、判断和返工，默认能辨认主干；展开/折叠、聚焦与整理布局可用 | 长名称、小屏、多个条件/回边、手动位置、运行中状态更新、隐藏节点有失败/反馈；整理不改变业务结构 | 布局/投影验证及真实前后端 fake Playwright，桌面和窄屏受控截图人工检查；不要求为纯展示重复付费调用 |
| 第三批：面板整理 | 人工和协调者均能查看结果、提交/处理反馈、局部改图并核对生效范围，主要动作在当前上下文可找到 | 模板/运行/历史切换、未保存草稿与服务端变更冲突、刷新/重连、键盘/焦点、Guest 权限、取消协调但保持其他任务 | 真实前后端 fake 浏览器完整操作链、原节点编辑/图管理/草稿恢复相关回归与截图；不另开与 UI 无关的收费验收 |

第一批至少区分三类受控案例：实现缺陷进入局部修复；互相矛盾的验收说明进入责任裁决；缺少执行/浏览器验证能力保持待验证并安排适当处理。不能只验证一条正常成功反馈，也不能为让用例通过而把不确定结果改成 true。

第一批真实 Provider 验证已沿用既有标准真实 World、独立命令与保留规则，覆盖实际读取、反馈、局部补图、文件修改与再次读取验证。精确竞争、重复与恶意参数由 fake/确定性测试覆盖。此次结果不自动要求后续纯展示任务重复收费验收。

三批共同完成的标准是：**人能读懂图、节点意见有去向、协调者能在授权内正确处置、局部修正能真实生效且可复核，界面能清楚表达这些操作及其影响。**
