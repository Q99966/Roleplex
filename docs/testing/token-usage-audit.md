## 转换链与实际输出上限

- run_agent 对每个模型 run_id 保留最新流 usage，模型结束时优先使用完整输出的 usage，只追加一次；最后逐请求求和。
- normalize_provider_usage 在 usage_metadata.output_tokens、原始 output_tokens/completion_tokens 中选择，不再次相加推理子项。
- 当前前端没有这份 usage 的累计计数逻辑；角色设置中的“输出预留”属于本地上下文预算。
- 历史 provider.built 的 param_keys 为空；当前同一角色 params_json 也是空。历史事实以日志为准，不拿当前配置倒推历史。
- 当前安装的 ChatOpenAI 在空参数配置下 max_tokens=None，离线检查实际构造 payload 不含 max_tokens/max_completion_tokens。
- ContextBuilder 和前端角色设置默认预留 1,024 输出 Token，但该预留**不等于发给 Provider 的输出上限**。
  原请求的实际上限取决于接入端默认行为；不能凭 65,536 就断言默认上限或触顶。

本机核对版本：langchain-openai 0.3.1、langchain-core 0.3.36、openai 1.109.1。
适配器会累加多个分片的 usage；兼容端若反复发送累计 usage，存在放大统计的风险。
历史没有原始帧，不能据此确认风险在当时发生；下面的小请求没有复现该风险，也不代表排除了长输出才出现的协议差异。

## 无法还原与后续建议

旧 provider.call_completed 未记录原始 usage 明细、reasoning_tokens 或 finish_reason。
当前规范化会丢弃 SDK 的 output_token_details.reasoning，结束事件也没有透传模型终止原因；历史消息不能补回这些字段。
因此本次能确认累计一致、当前小请求转换一致、存在未展示的推理开销、原请求未显式设置输出上限；
不能确定历史 65,536 中代码/推理各占多少，也不能断言是否达到 Provider 上限。

若继续增强诊断，最小范围是保存白名单原始 usage 数值、规范化值、推理子项、终止原因、请求上限及尝试身份；
字段缺失保持 unknown/null，不保存完整正文。配置中的本地输出预留和 Provider 实际上限需明确区分，不能静默把预留值变成低输出硬限制。
